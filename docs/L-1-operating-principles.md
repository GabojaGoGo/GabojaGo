# L-1 · 개발 운영 원칙

특정 프로젝트에 한정하지 않는다. 모든 설계·구현·리뷰 작업에 기본으로 적용한다.

프로젝트별 맥락은 `docs/L0-project-context.md`에, 저장소 작업 규칙은 `AGENTS.md`에 있다.

> **빠진 건 적극적으로 찾아라. 하지만 상상해서 만들지는 말고, 실제 증거를 보고 지금 필요한 것만 구현하라. 그리고 한 번 확정한 건 새 근거가 생기기 전까지 계속 뒤집지 마라.**

---

## 1. 핵심 원칙 — 능동적 누락 탐지

시키지 않은 사항이라도 현재 작업의 성공이나 향후 확장에 중요한 **누락된 요구사항·의존성·위험·운영 요소**를 능동적으로 찾는다.

단, **미래에 필요할 것 같다는 이유만으로 상상해서 구현하지 않는다.**

발견한 항목은 근거를 확인한 뒤 셋 중 하나로 분류한다.

| 분류 | 정의 | 행동 |
| --- | --- | --- |
| `NOW` | 현재 마일스톤이 정상 동작하려면 지금 필요한 것 | 구현한다 |
| `CONTRACT-ONLY` | 지금 없어도 되지만, 나중에 넣으면 데이터·API·스키마·아키텍처를 크게 깨뜨리거나 마이그레이션 비용이 큰 것 | schema · interface · enum · reference · extension point 등 **최소 계약만** 확보한다 |
| `LATER` | 지금 불필요하고, 실제 요구가 생긴 뒤 넣어도 크게 깨지지 않는 것 | 구현하지 않는다 |

---

## 2. 추측 금지

누락을 발견했다고 바로 구현하지 않는다. 아래 중 하나 이상을 근거로 판단한다.

- 실제 코드
- 실제 데이터
- 테스트 결과
- 실행 로그 · Trace
- 사용자 요구사항
- 현재 시스템 제약
- 공식 문서 · 외부 시스템 계약
- 이미 확정된 로드맵

근거가 부족하면 **가설로 표시하고 구현하지 않는다.** 필요하면 가장 작은 실험이나 Walking Skeleton으로 먼저 확인한다.

명세에 적힌 수치와 실제 값이 다를 수 있다. 문서를 근거로 삼기 전에 실측으로 대조한다.

---

## 3. 과설계 방지

새 구성요소를 추가하려 할 때 반드시 묻는다.

1. 이것이 **현재 관측된 문제**를 해결하는가?
2. 지금 넣지 않으면 나중에 **실제로 비싼 변경**이 되는가?

둘 다 아니면 `LATER`로 보낸다.

---

## 4. Walking Skeleton 우선

전체 시스템을 미리 완성하려 하지 않는다. 가능한 한 빨리 실제 입력이 끝까지 한 번 관통하게 만든다.

```
Input → Core Logic → External Dependency → Output → Validation → 기록
```

실제 실행에서 얻은 데이터와 실패를 다음 설계의 근거로 쓴다.

한 번에 여러 문제를 섞지 않는다. 첫 관통은 변수를 하나로 줄여 실패 원인을 가릴 수 있게 만든다.

---

## 5. 변경 판단 순서

새 아이디어나 기술을 마주쳤을 때 순서대로 묻는다.

1. 현재 문제를 해결하는가?
2. 실제 근거가 있는가?
3. 지금 필요한가?
4. 계약만 확보하면 되는가?
5. 나중에 추가해도 싼가?
6. 도입 비용보다 얻는 가치가 큰가?

그 뒤 `NOW` / `CONTRACT-ONLY` / `LATER` 중 하나로 분류한다.

---

## 6. 확정된 결정은 근거가 깨졌을 때만 수정한다

> 필요한 것은 확인하고, 결과는 모두 기록하며, 기존 결정의 근거가 깨졌을 때만 그 근거를 대고 **깨진 범위만** 수정한다.

현재 결정에 필요한 사실은 추측하지 않고 **확인**한다. 확인 결과는 기존 판단과 일치하는지와 관계없이 그대로 받아들이고 기록한다. **불편한 결과를 숨기거나 기존 결정에 맞춰 해석하지 않는다.**

확인된 사실이 기존 결정의 **전제·적용 범위·결론**을 깨뜨렸을 때는 무엇이 깨졌는지 근거를 남기고 **그 범위만** 수정한다. 그렇지 않으면 확정된 결정을 다시 열지 않는다.

### 확인된 사실이란

실측만이 아니다. 아래가 모두 포함된다.

- 실제 데이터·코드·테스트·실행 로그로 측정한 값
- 외부 계약·제약의 확인 결과 (API 정책, 승인 요건, 이용조건)
- 사용자의 명시적 요구사항 변경

"더 나은 방법이 생각났다", "이게 더 깔끔하다"는 확인된 사실이 아니다. 그런 생각이 들면 `LATER`에 적어두고 현재 결정으로 계속 간다.

### 판정 절차

```text
확인된 사실이 나옴
  ↓
기존 결정의 전제 / 적용 범위 / 결론 중 하나가 깨졌나?
  ├─ YES → 무엇이 깨졌는지 기록 + 깨진 범위만 수정
  └─ NO  → 결과만 기록 + 기존 결정 유지
```

### 결론에는 측정 범위를 함께 적는다

**범위 없는 결론은 기록하지 않는다.** 결론만 적으면 측정한 것보다 넓게 단정한 것을 스스로 알아채지 못한다.

```text
나쁨   지번주소는 원천 공통으로 채움률이 높다
좋음   지번주소 채움률 높음  [측정: 주차장·일반음식점 2개 원천]

나쁨   이 원천을 채택한다
좋음   base로 잠정 사용  [측정: 권위성·완전성·연결성. 핵심 기준인 최신성 미측정]
```

범위는 최소한 다음을 담는다.

```text
어떤 대상을 / 몇 개를 / 어느 조건에서 쟀는가
재지 않은 것은 무엇인가
```

`전부`·`공통으로`·`항상` 같은 표현을 쓸 때는 측정 범위가 실제로 전체를 덮는지 확인한다. 덮지 않으면 범위를 좁혀 쓴다.

**결과가 기존 결정을 지지해도 기록한다.** 이것이 없으면 몇 주 뒤에 같은 조사를 다시 한다. "문제없음"도 그 결정을 계속 믿어도 되는 근거이므로 자산이다.

기록 항목은 다음으로 충분하다.

```text
대상 결정 / 확인한 내용 / 결과 / 영향 / 날짜
```

### 부재를 일반화하지 않는다

**특정 원천에 값이 없다는 사실은 그 원천에 대한 결론일 뿐, 그 사실 자체가 확보 불가능하다는 근거가 아니다.** 한 원천의 실측 0%를 "원천 없음"으로 확대하면, 그 사실을 실제로 관리하는 기관을 찾지 않은 채 요구사항을 지운다.

어떤 사실을 "확보 불가능"으로 판정하려면 아래를 모두 확인하고 기록해야 한다.

```text
1. 범용 공개데이터 검색
2. 그 사실을 관리할 만한 분야별 전문기관
3. 대상 지역의 지자체·산하기관 원천
4. 이용 가능한 민간 원천 (약관·저장 조건 확인 포함)
5. 이미 보유한 데이터에서 계산·추출할 가능성
```

다섯 가지를 다 확인하기 전 상태는 "확보 불가능"이 아니라 **탐색 미완**이다. 둘을 같은 이름으로 부르면 미완이 결론으로 굳는다.

**단, 탐색은 현재 결정에 필요한 사실에 대해서만 한다.** 판정할 일이 없는 사실까지 다섯 범위를 도는 것은 과설계다.

탐색 결론에는 **조사한 범위와 조사하지 않은 범위를 함께** 적는다. 범위 없는 "없음"은 기록하지 않는다.

### 확정의 판정

**"확정"은 단계가 아니라 결정 단위다.** 어떤 결정은 초기에 확정되고, 어떤 결정은 후반까지 미확정일 수 있다. 프로젝트 단계 전체를 통째로 동결하지 않는다.

확정 여부는 프로젝트 컨텍스트 문서의 확정된 결정 표에 **행이 있는지**로 판정한다. 표에 없으면 미확정이며, 미확정 설계는 근거 있는 개선 제안을 받는다.

### 구현과의 관계

**확정된 결정을 유지하는 것과 구현 오류를 방치하는 것은 다르다. 구현이 확정된 결정과 다르면 즉시 수정한다.** 결정이 확정됐다는 것은 코드를 건드리지 말라는 뜻이 아니다.

반대로 **확인된 사실이 결정을 뒤집으면 즉시 반영한다.** 문서에 적혀 있다는 이유로 틀린 결정을 유지하지 않는다.

## 7. 마일스톤 종료 점검

매 마일스톤이 끝날 때 한 번 수행한다.

> 이 시스템이 다음 단계까지 확장된다고 가정했을 때, 지금 확보하지 않으면 데이터 마이그레이션·API 파괴·대규모 재작업·보안 문제·운영 사고로 이어질 것은 무엇인가?

해당 항목만 `CONTRACT-ONLY` 또는 `NOW`로 끌어올린다. "언젠가 필요할 수도 있다"는 이유로는 끌어올리지 않는다.

종료 보고에 최소한 다음을 남긴다.

- **NOW 완료** — 반드시 필요했던 것은 구현됐는가
- **CONTRACT-ONLY** — 비싼 변경이 될 항목의 계약은 확보됐는가
- **LATER** — 의도적으로 미룬 것은 무엇인가
- **새로 발견된 누락** — 실행하면서 무엇을 새로 알게 됐는가
- **근거** — 코드·데이터·테스트·Trace 중 무엇이 판단 근거인가
- **기술 부채** — 이번 선택 때문에 나중에 갚을 비용이 있는가
- **다음 단계** — 현재 데이터가 다음 구현을 정당화하는가

## 8. 검증의 검증

검사 스크립트가 통과했다고 결과가 옳은 것은 아니다. 검사기 자체가 틀릴 수 있다.

- 개수만 세지 말고 **방향·의미**까지 확인한다
- 페이지네이션이 있는 조회는 **마지막 페이지까지** 돌고 total과 대조한다
- 변경 후에는 **재조회**로 확인한다. 요청이 성공했다는 응답만으로는 부족하다
- 일괄 변경은 작은 배치로 나누고, 각 배치 검증을 통과한 뒤 다음으로 간다
- 오류가 나면 이후 배치를 멈추고 정상 반영 범위·실패 범위·원인을 보고한다

---

## 9. 최우선 행동 규칙

> 시키지 않은 누락까지 능동적으로 찾아라.
> 다만 상상으로 구현하지 마라.
> 실제 데이터와 실행 결과로 확인하고 `NOW` / `CONTRACT-ONLY` / `LATER`로 분류하라.
> 매 마일스톤 종료 시 "지금 안 하면 나중에 비싸지는 것은 무엇인가"를 다시 검토하고 그 항목만 끌어올려라.
> 한 번 확정한 것은 새 근거가 생기기 전까지 뒤집지 마라.

목표는 미래를 전부 예측하는 것이 아니다. **과설계를 피하면서 나중에 비싸게 깨질 결정만 미리 보호하는 것**이다.
