# L0 · 프로젝트 컨텍스트

가보자GO 작업 시 항상 전제로 삼는 맥락. 운영 원칙은 `docs/L-1-operating-principles.md`.

---

## 1. 목적

상황 기반 장소·루트 추천 엔진. 겉은 국내여행 코스 추천이지만 내부는 여행 전용으로 닫지 않는다.

> 사용자의 상황·목적·이동수단·시간대·동행을 고려해 실패 확률이 낮은 장소와 루트를 추천한다.

- **1차 목표**: 부산·울산·경남 MVP 출시
- **두 사용 방식**: 일상(목적지 1개 탐색) / 여행(슬롯 기반 코스 + 슬롯별 교체)
- 둘은 별개 기능이 아니라 **같은 탐색 엔진을 다른 상황에서 쓰는 것**이다

해결하는 문제는 "장소를 못 찾는 것"이 아니라 **목적 적합성 검수와 동선 조합, 현장 변수 재조정이 전부 사용자 몫**이라는 점이다.

## 2. 도메인 모델

### 2-1. 데이터 4층

```
staging          원천이 준 원본. 삭제하지 않고 보존
PlaceInfo        원천 사실을 가공 없이 저장       주차면 수 20대
PlaceAttribute   사실을 해석·등급화한 장소 특성   주차 편의성 HIGH
PURPOSE          Attribute 조합으로 계산한 목적 적합성
```

`Place` 컬럼은 장소를 식별·위치시키는 값만 담는다. **신규 컬럼 추가는 금지가 기본**이며, 식별·위치·전역 조회에 반드시 필요할 때만 별도 설계 결정 후 예외 추가한다. `phone`·`imageUrl`은 기존 예외로 유지한다.

### 2-2. 분류 3축

| 축 | 질문 | 코드 |
| --- | --- | --- |
| SUBTYPE | 이 장소가 무엇인가 | `PlaceSubtypeCode` (64개, 업종·시설 종류) |
| ATTRIBUTE | 어떤 특성을 갖는가 | `AttributeKey` (34개) |
| PURPOSE | 어떤 상황에 적합한가 | `PlacePurposeCode` (현재 3개) |

**축을 섞지 않는다.** "중식 제외"는 종류 조건이고 "데이트하기 좋은 곳"은 목적 조건이다. 감성카페처럼 특성 조합에서 도출되는 개념을 SUBTYPE에 넣지 않는다.

### 2-3. 데이터 상태 — 판단 단위 3종

하나의 status 컬럼이나 enum으로 합치지 않는다.

```
장소 × InfoKey (현재 상태)    PRESENT / NOT_APPLICABLE / NO_SOURCE
수집 run 결과                 PARSE_SUCCEEDED / MISSING / PARSE_FAILED
PlaceAttribute (현재 값)      UNKNOWN
```

장소별 행으로 저장되는 것은 `PRESENT`와 `UNKNOWN` 둘뿐이다. `NOT_APPLICABLE`은 적용 규칙에서, `NO_SOURCE`는 원천 매핑표에서 계산된다. 규칙에서 계산되는 값을 데이터로 저장하면 규칙이 바뀔 때마다 전량 재적재해야 한다.

### 2-4. 커버리지 지표 2종

분모가 다르다. 섞으면 원천에 없는 값을 파이프라인 탓으로 돌리게 된다.

```
파이프라인 품질  = PARSE_SUCCEEDED / (PARSE_SUCCEEDED + MISSING + PARSE_FAILED)
                  단위는 수집 run. 판정은 해당 차수의 최종 run 기준
                  → 적용 차수의 완료 게이트

추천 데이터 확보율 = PRESENT인 place × required InfoKey / 적용 가능한 전체
                  단위는 장소 × InfoKey. NO_SOURCE 포함
                  → 게이트가 아니라 위험 지표. 추천 기능 적용 전에 다시 게이트로 판단
```

## 3. 아키텍처

```
data-import (Python)   공공 원천 수집 → staging → MySQL 적재
      ↓
gabojago-backend       Java 21 · Spring Boot · Gradle · MySQL/Redis
      ↓                OSRM (자동차·도보 경로)
gabojago-frontend      Flutter · Dart
```

- 원천 정의는 **Java enum이 단일 원본**, `CategoryDefinitionSynchronizer` 방식으로 DB 테이블에 동기화하고 Python이 그 테이블을 읽어 검증한다
- 원천 필드 매핑·파서·**원천 우선순위는 `data-import/mappings`가 소유**한다. 소비 주체가 Python이므로 Java enum에만 두면 importer가 읽을 수 없다
- 배포는 현재 iMac (`gabojago-backend/scripts/deploy-imac.sh`)

## 4. 확정된 결정

**이 표에 행이 있으면 확정, 없으면 미확정이다.** 확정 여부를 판정하는 곳은 여기뿐이다. 작업을 시작하기 전에 먼저 확인하고, 여기 있는 것은 다시 설계하지 않는다.

확정된 항목은 확인된 사실이 그 전제·적용 범위·결론을 깨뜨렸을 때만, 깨진 범위만 수정한다. 미확정 설계는 근거 있는 개선 제안을 받는다. 검증·변경 이력은 [`decision-log.md`](decision-log.md)에 남기고 이 표에는 현재 상태만 유지한다.

재논의를 열 수 있는 근거와 판단 절차는 `docs/L-1-operating-principles.md` 6절을 따른다. 이 문서에서 반복하지 않는다.

**구현이 이 표와 다르면 즉시 고친다.** 결정이 확정됐다는 것은 코드를 건드리지 말라는 뜻이 아니다.

| 결정 | 내용 |
| --- | --- |
| Info/Attribute 경계 | 원천 값을 그대로 저장하면 Info, 해석·등급화하면 Attribute. Info가 바뀌면 Attribute를 재계산한다 |
| InfoKey 적용 범위 | 공통 / PlaceType / PlaceSubtype 3단계. 가장 좁은 단위로 선언한다 |
| InfoKey 필수 개념 | 두지 않는다. InfoKey는 허용 어휘이고 필수·선택은 Attribute에만 붙는다 |
| Info 불일치 처리 | `PlaceCategoryStatus`를 변경하지 않는다. staging 보존 + 별도 검수 사유로 집계하고 반복 패턴이면 규칙을 고친다 |
| 원천 선택 단위 | 원천 전체의 우열을 매기지 않는다. **사실별로** 권위성·완전성·연결성·최신성을 실측해 정한다. 종합점수를 쓰지 않으며, 해당 사실의 핵심 기준을 못 넘으면 다른 장점이 있어도 탈락한다. 실측 전에는 채택이 아니라 **후보**다 |
| 채택 후 값 선택 규칙 | 동일한 정보를 여러 원천이 제공하면 **실측을 통해 채택된 우선 원천**의 값을 쓴다. 우선 원천의 값이 없거나 유효하지 않을 때만 검증된 보조 원천을 쓴다. **갱신 시점이 더 최신이라는 이유만으로 우선순위를 뒤집지 않는다.** 어느 원천이 우선인지는 여기서 정하지 않고 [`other-source-survey.md`](../data-import/docs/other-source-survey.md) 1절이 소유한다 |
| 원천 부재 판정 | 특정 원천의 실측 0%를 `NO_SOURCE`로 쓰지 않는다. 공개데이터 검색 · 분야별 전문기관 · 부울경 지자체 원천 · 민간 원천(약관 포함) · 기존 데이터의 계산·추출 가능성 **다섯 범위를 모두 확인하고 기록했을 때만** `NO_SOURCE` 후보로 내린다. 그 전 상태는 `SOURCE_SEARCH_PENDING`이다 |
| `SOURCE_SEARCH_PENDING`의 위치 | 장소별로 저장하는 값이 아니라 **`data-import/mappings/attribute_sources.csv`의 `status`** 값이다. `NO_SOURCE`가 원천 매핑표에서 계산되는 것과 같은 층이다(2-3절) |
| 다중 원천 병합 | 자동 병합 임계값을 보수적으로 잡고 모호한 후보는 병합하지 않는다. 오병합은 되돌리기 어렵고 중복은 나중에 합칠 수 있다 |
| 첫 사이클 범위 | 단일 원천으로만 한 바퀴 돈다. 파싱 문제와 장소 병합 문제를 섞지 않는다 |
| 필수 판정 | 수집 가능성을 섞지 않는다. 못 채우는 속성을 필수에서 빼면 게이트가 무의미해진다 |
| 원천 채택 절차 | 조사 문서·포털 명세만 보고 채택하지 않는다. 공식 원천 중 subtype에 직접 대응하는 후보는 전체 파일을 받아 실측한 뒤 비교한다. 컬럼 수·인코딩·좌표계·채움률은 파일을 열어야만 알 수 있다. 채움률에는 **매칭에 쓸 지번·도로명주소**를 반드시 포함한다 |
| 다운로드의 목적 | 다운로드는 DB 적재가 아니라 raw/staging 품질 측정이다. 실측을 통과한 원천만 적재 대상이 된다 |
| 원천 운영 모델 — 세 축 | 원천마다 **기준선**(전체 CSV 또는 API 전량 조회), **변경 감지**(변경 API·수정일 조회·재다운로드 대조), **종료 신호**(명시 상태 또는 미관측 임계)를 각각 따로 정의한다. 원천 종류로 일괄 규정하지 않는다 |
| 변경 감지 ≠ 실제 갱신 | 변경 API·수정일·새 CSV는 모두 **재검토 후보 신호**다. 실제 갱신은 의미 있는 필드 비교로만 반영한다. 비교 대상 필드 목록은 원천별 계약이며 **버전을 갖는다**. 수집 메타데이터(데이터갱신시점·최종수정시점 등)는 비교에서 제외하고, 공백·표기는 정규화 후 계산한다. 목록 버전이 올라가면 전부 변경으로 처리하지 않고 새 버전 기준으로 기준선을 다시 계산한다 |
| 미관측 ≠ 종료 | 미관측 레코드를 즉시 삭제·폐업으로 판정하지 않는다. 원천이 **명시적 종료 상태를 주면 그 값을 따른다**(인허가의 `영업상태명=폐업`, `폐업일자`). 종료 표시가 없는 원천(표준데이터)에만 **원천별 미관측 임계**를 둔다 |
| 미관측 임계 도달 시 처리 | 삭제·폐업으로 기록하지 않는다. `PlaceInfo`와 `PlaceSourceRecord`, 마지막 확인 정보는 **보존**하고 **추천 후보에서만 제외**한다. 재등장하면 후보로 복귀한다. 노출 제외는 원천 사실이 아니라 판단이므로 `PlaceAttribute` 층에서 처리한다 |
| 수집 실패의 처리 | 파일·API 수집 실패나 부분 응답에서는 `last_seen`을 갱신하지 않는다. 실패를 미관측으로 취급하면 정상 레코드가 임계에 도달한다 |
| 표준데이터 비교 단위 | 파일 단위가 아니라 **원본 ID + 행별 데이터기준일자 + 마지막 정상 snapshot 관측값**으로 비교한다 |
| 실측 범위 | 현재 결정에 쓰이는 원천만 실측한다. base 결정과 무관한 원천은 해당 subtype 작업 시점에 잰다. 단 승인 대기가 있는 원천은 실측 전이라도 활용신청을 먼저 넣는다 |

## 5. 알려진 제약

`구분`은 읽는 사람이 무엇을 해야 하는지 가른다. **확정**은 받아들이고 설계에 반영한다.
**조사**와 **보류**는 후속 이슈가 있어야 하며, 확인 결과는 [`decision-log.md`](decision-log.md)에 남긴다.

| 구분 | 제약 | 내용 | 후속 |
| --- | --- | --- | --- |
| 확정 | 상세 필드 미수집 | 수집된 장소 데이터는 목록 조회 응답이다. `parking`·`usetime`·`usefee`·`spendtime`이 없다. 상세 조회는 별도 호출이 필요하다 | `GO-73` |
| 확정 | 다중 원천 불가 | `places`에 `UNIQUE(source_type, source_place_id)`가 있어 한 장소가 원천 식별자를 한 쌍만 갖는다. 제약을 없애는 게 아니라 `PlaceSourceRecord`로 **위치를 옮겨야** 한다 | `GO-99` |
| 확정 | 좌표계 혼재 | 원천별로 다르다. 주차장 표준데이터는 WGS84라 변환이 불필요하고, 식품 인허가 계열은 EPSG:5174 계열이라 변환이 필요하다. 상가정보는 명세상 WGS84이나 실측 전이다 | `GO-94` |
| 확정 | 호출 쿼터 | 개발계정 1,000회/일이다. 운영계정 전환은 활용사례 등록(서비스 URL·캡처·개시일)을 요구해 출시 전에는 불가능하다 | `GO-67` |
| 확정 | 예산 | 없다. 유료 데이터·유료 API는 검토 대상이 아니다 | — |
| 확정 | 목적 필터 원천 없음 | `NOISE_LEVEL`·`OUTLET_ACCESSIBILITY`·`WIFI_STABILITY`·`SEAT_SPACING` 등은 어느 공공 원천에도 없다. 원천 운영 모델을 아무리 개선해도 해결되지 않는다. 행정 사실 품질과 목적 필터 가용성은 다른 축이다 | — |
| 확정 | 표준데이터 기준일 혼재 | 표준데이터 전체 파일은 한 시점의 스냅샷이 아니다. 주차장 CSV에서 `데이터기준일자`가 행마다 달랐다(2026-04-16·17·22). 파일 단위가 아니라 행별로 비교해야 한다 | — |
| 확정 | 매칭 키 편차 | 지번주소는 **현재 확인한 두 원천**에서 채움률이 높다(주차장 98.6%, 일반음식점 100%). 도로명주소는 편차가 크다(주차장 29.8%, 일반음식점 99.3%). **현재 확인 범위에서는** 지번을 기본 키로 쓰고 도로명은 양쪽 원천에 모두 있을 때만 보조 키로 쓴다 | — |
| 조사 | 원천별 종료 계약 미확인 | TourAPI와 상가정보가 종료·삭제를 어떻게 표현하는지 확인하지 않았다. 인허가(명시 상태)와 표준데이터(표시 없음) 중 어느 쪽인지 실측 전에는 모른다 | `GO-122` |
| 조사 | 인허가 증분 기준 적합성 미확정 | 부산 일반음식점 영업중 42,178건 중 `데이터갱신시점`이 2026-05인 것이 19,627건(47%)이다. 실제 개·폐업이 아니라 원천 일괄 갱신으로 보인다. `DAT_UPDT_PNT` 증분이 실사용 가능한지 측정 전이다 | `GO-123` |
| 보류 | 미관측 임계값 미확정 | 표준데이터의 미관측 임계(횟수·기간)를 정하지 않았다. 원천별 파일 갱신 주기와 업로드 지연 분포를 실측한 뒤 정한다. 주차장 원천이 반기 단위로 실질 갱신된다면 90일은 너무 짧다 | `GO-124` |

## 6. 실행 단계

Epic은 **책임 영역**(기준 정의 / 데이터 파이프라인 / 추천 활용), Fix Version `P0~P6`은 **실행 시점**이다. 두 축은 교차하며 서로를 대체하지 않는다.

```
P0 원천 접근 준비 → P1 상세 실측 → P2 분류 기준 확정
```

## 7. 근거로 삼을 수 있는 것

`L-1`의 "추측 금지"에서 요구하는 근거는 이 저장소에서 다음을 뜻한다.

- `gabojago-backend/src` — enum·엔티티·제약이 실제 계약이다
- `data-import/mappings/*.csv` — 원천 매핑과 채움률. **단, 명세 기반 추정치가 섞여 있어 실측과 대조해야 한다**
- `data-import/data/` — 실제 수집된 원본
- `data-import/docs/other-source-survey.md` — 원천별 적재 계획과 우선 원천
- Jira `GO` 프로젝트 — 작업 이력·의존 순서·미결 항목·결정 근거. **확정 여부는 여기서 판정하지 않는다**(4절)
- 테스트·`make verify` 결과
