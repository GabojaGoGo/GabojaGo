# 원천 값 → 분류 매핑과 확장

원천이 준 응답 값을 `PlaceSubtypeCode`·`InfoKey`·`AttributeKey`로 옮기는 **규칙과 절차**를
소유한다. 실제 매핑 값은 `mappings/*.csv`가 갖는다. 값이 이상해 보이면 이 문서에서 그 값의
규칙을 먼저 찾는다.

- 무엇을 쪼갤 수 있는지(확장 후보 목록): [`other-source-survey.md`](other-source-survey.md) 3절
- Info와 Attribute의 경계: [`info-attribute-split.md`](info-attribute-split.md)
- 각 수치의 측정 범위: [`attribute-coverage.md`](attribute-coverage.md)
- 확장 조건(확정): [`L0` 4절](../../docs/L0-project-context.md) `분류 축의 확장 조건`·`원천 저장 범위`

---

## 1. 경로

원천 응답은 두 갈래로 갈린다. **갈리기 전에 원본을 staging에 전량 보존한다.**

```text
원천 응답 (CSV 행 · API 응답)
      │
      └─ staging 원본 보존 ─────────── 매핑이 없는 컬럼도 버리지 않는다
              │
              ├─ 종류를 말하는 값 ──→ PlaceSubtypeCode 배정
              │   (업종 파일명, 업태구분명, 분류코드)      mappings/*_subtypes.csv
              │
              └─ 사실을 말하는 값 ──→ InfoKey 원문 저장 ──→ AttributeKey 파생
                  (영업시간, 주차, 객실수)      해석 없이 그대로      해석·등급화
```

**보존이 확장의 전제다.** 지금 매핑이 없는 컬럼이 나중에 축을 세분화할 유일한 재료다.
버리면 그 시점에 원천을 다시 받아야 한다.

## 2. subtype 배정

### 파일 규약

원천마다 `mappings/<원천>_subtypes.csv`를 둔다. 현재 `tour_api_subtypes.csv`(239행)가
유일하며, 이 컬럼 구성을 표준으로 쓴다.

| 컬럼 | 뜻 |
| --- | --- |
| `source_*` | 원천이 준 분류 값 (콘텐츠 타입, 분류코드, 업종·업태명) |
| `target_place_type` · `target_subtype_code` | 배정할 `PlaceType`·`PlaceSubtypeCode` |
| `mapping_status` | `CONFIRMED` / `NEEDS_REVIEW` |
| `source_count` | 그 값의 실측 건수 |
| `sample_titles` | 판정 근거가 된 실제 상호 예시 |

`sample_titles`는 장식이 아니다. 값 이름만 보고 배정하면 틀리며(3절), 나중에 다른 사람이
판정을 재검토할 때 필요한 유일한 증거다.

### 현재 상태

| 원천 | 매핑 파일 | 상태 |
| --- | --- | --- |
| TourAPI | `tour_api_subtypes.csv` | 239행 — `CONFIRMED` 182 · `NEEDS_REVIEW` 57 |
| 인허가 (식품·문화·생활) | `license_subtypes.csv` | 98행 — `CONFIRMED` 40 · `NEEDS_REVIEW` 37 · `UNMAPPED` 21 |
| 상가정보 | **없음** | 대·중·소분류 3단계 보유. 미대조 |
| 주차장 표준데이터 | 불필요 | `PARKING_LOT` 단일 |

`license_subtypes.csv`의 키는 **(업종 파일, `업태구분명`)** 이다. `업태구분명` 컬럼이 없는
업종(농어촌민박업·공연장 등)은 업태를 빈값으로 두고 업종 자체가 subtype을 결정한다.

`mapping_status` 어휘는 3종이다. `tour_api_subtypes.csv`의 2종에 `UNMAPPED`를 더했다.

| 값 | 뜻 | target 컬럼 |
| --- | --- | --- |
| `CONFIRMED` | 업태 값이 subtype에 대응하고 표본도 일치 | 채운다 |
| `NEEDS_REVIEW` | 대응이 애매하거나 값 신뢰도가 낮다 | 확실할 때만 채운다 |
| `UNMAPPED` | 고정 장소가 아니거나 대응 subtype이 없거나 노출 정책 미결 | **비운다** |

**추측으로 채우지 않는다.** `CONFIRMED`가 아닌 행에는 사유를 반드시 적는다.

[측정: 2026-08-22 LOCALDATA 지역별 전체 부울경 영업중, 27개 업종 파일 169,086건]

| 상태 | 행 | 건수 | 비율 |
| --- | ---: | ---: | ---: |
| `CONFIRMED` | 40 | 111,207 | 65.8% |
| `NEEDS_REVIEW` | 37 | 51,880 | 30.7% |
| `UNMAPPED` | 21 | 5,999 | 3.5% |

**부울경 195개 업종 중 27개만 매핑했다.** 나머지는 `PlaceSubtypeCode`에 대응 후보가 없어
대상에서 뺐다.

## 3. 배정 시 실제로 틀리는 지점

측정에서 확인된 것만 적는다. 규칙을 만들 때 반드시 검토한다.

**원천 업종은 `PlaceType` 경계를 넘는다.** `휴게음식점`은 이름상 CAFE 계열이지만 안에
**편의점 3,945건**이 있고 이건 `SHOP`의 `CONVENIENCE_STORE`다. 파일 단위로 PlaceType을
정하면 틀린다. 배정 단위는 파일이 아니라 **업태 값**이다.

**한 subtype이 여러 원천에서 온다.** `PENSION_HOMESTAY`는 농어촌민박업(4,823)과
관광펜션업(209) 양쪽에 있고 법적 근거가 다르다. 매핑은 원천별로 따로 쓰되 같은
`target_subtype_code`를 가리킨다.

**현재 축이 원천보다 거칠다.** 유흥주점 13개 업태가 `GENERAL_BAR`·`TRADITIONAL_PUB` 2개에
뭉치고, 체육도장·체력단련장·수영장이 `SPORTS_FACILITY` 1개에 뭉친다. 이때 `업태구분명`
원문을 staging에 남겨야 나중에 쪼갤 수 있다. 목록은 survey 3절에 있다.

**값 이름이 내용을 보장하지 않는다.** 컬럼이 있어도 값이 없을 수 있다 — 농어촌민박업의
`조식제공여부`·`건물형태구분명`·`화장실종류명`은 채움률 **0.0%**다. 매핑을 만들기 전에
채움률을 먼저 잰다.

## 4. Attribute 파생

### 현재 막혀 있는 지점

`attribute_sources.csv`는 "어느 원천 필드가 어느 `AttributeKey`에 대응하는가"까지만 갖고
있다. **원천 값을 허용 어휘로 바꾸는 규칙은 아직 없다.** `FREE_TEXT` 13개 조합이 전부 여기서
막혀 있다.

```text
원천 값                                          허용 어휘
parkingfood  = "가능"                    →   GOOD / NORMAL / LIMITED /
opentimefood = "- 목요일~금요일 11:00~20:00"      NEARBY_PARKING / DIFFICULT / UNKNOWN
restdatefood = "매주 일요일~수요일"        →   LATE / NORMAL / EARLY_CLOSE / UNKNOWN
```

변환 규칙을 만들려면 **원본 값 분포를 먼저 집계해야 한다.** 아직 하지 않았다. 분포를 보지
않고 5단계·3단계를 나누면 실제로는 한 값에 몰리는 구분을 만들게 된다 — 산림청 등산로
난이도가 산 단위 집계에서 98.0%가 `쉬움`으로 몰린 것이 그 사례다.

이번 P2-D에서 확정하지 않는다.

입력이 제공되면 `scripts/analyze_tour_api_food_fields.py`가 기존 응답을 스트리밍 집계한다.
이 분석은 앞뒤 공백만 제거한 원문 빈도, HTML·시간·요일·한국어 단위 신호, 필드 없음·빈값·상세
미등록·파싱 실패를 분리해 report로 기록하며, **등급·enum·임계값을 정하지 않는다.**

### 규칙을 확정하는 순서

```text
1. 해당 필드의 원본 값 분포 집계        (전량 또는 층화표본, 범위 기록)
2. 값이 실제로 갈리는 경계 확인          몰리면 단계 수를 줄인다
3. 변환 규칙을 mappings에 값으로 기록     규칙은 이 문서, 값은 csv
4. 역변환 표본 검수                     변환 결과를 원문과 대조
```

3번 전까지는 `PlaceInfo`에 원문만 저장하고 `PlaceAttribute`는 `UNKNOWN`으로 둔다.
해석하지 않은 것과 해석해서 모른다는 것은 같은 값으로 저장되지만, 원문이 남아 있으면
규칙이 생겼을 때 재적재 없이 다시 계산할 수 있다.

### 담을 키가 없는 사실

원천에 값은 있는데 대응 `AttributeKey`가 없는 것이다. 새 키를 지금 만들지 않고 여기 적어만
둔다.

| 사실 | 원천 | 현재 상태 |
| --- | --- | --- |
| 근접 공영주차장 존재율 | 주차장 표준데이터 좌표 계산 | `PARKING_CONVENIENCE`와 **다른 사실**이라 넣지 않음. 별도 키 여부 미정 |
| 객실수 | 농어촌민박업 98.5% | `InfoKey` 후보 `ROOM_COUNT`만 있고 대응 `AttributeKey` 없음 |
| 화장실수 | 농어촌민박업 84.1% | 대응 키 없음 |

## 5. 확장 판정

새 `PlaceSubtypeCode`·`AttributeKey`를 만들 때 순서대로 묻는다. `L-1` 3절 과설계 방지를
따른다.

```text
1. 실제 추천 질의가 이 구분을 요구하는가      아니면 만들지 않는다
2. 원천이 그 구분을 실제로 주는가            채움률까지 확인. 컬럼 존재는 근거가 아니다
3. 값이 한쪽으로 몰리지 않는가              몰리면 구분이 생겨도 변별력이 없다
4. 기존 값으로 표현할 수 없는가             표현되면 매핑만 고친다
```

넷을 다 통과하면 enum에 추가하고, 매핑 파일과 `attribute_sources.csv`에 같은 커밋으로
반영한다. 통과하지 못하면 survey 3절 확장 후보 표에 근거와 함께 남긴다.

**"원천이 생겼다"만으로는 추가하지 않는다.** 원천 확보는 2번을 충족할 뿐이다.

## 5-1. 매핑 검증 방법

작성 후 반드시 돌린다. 구조 검사만으로는 오분류를 못 잡는다.

**누락** — 원본에서 `(업종, 업태)` 조합을 다시 추출해 csv와 대조한다. 조합 수·건수 합계가
모두 일치해야 한다. 2026-08-22 실행 결과 98/98 조합, 169,086건 일치, 누락·유령 0건.

**구조** — `target_subtype_code`가 enum에 실재하는가, `target_place_type`이 enum의 소속과
같은가, `CONFIRMED`에 target이 있는가, `UNMAPPED`에 target이 비었는가, 키가 유일한가.

**오분류** — 사업장명 키워드 적중률로 교차 확인하되 **반드시 대조군을 함께 잰다.**
적중률 단독으로는 판정할 수 없다. 상호에 업종명을 넣지 않는 가게가 많기 때문이다.

| 대상 | 적중률 | 해석 |
| --- | ---: | --- |
| 휴게음식점 `커피숍` (카페 키워드) | 56.2% | 기준선의 110배 — 값 신뢰 가능 |
| 일반음식점 `까페` (카페 키워드) | 15.1% | 커피숍의 1/4 — 부분적으로만 맞다 |
| 일반음식점 `한식` (카페 키워드) | **0.8%** | 오적중 기준선 |
| 일반음식점 `중국식` (카페 키워드) | **0.2%** | 오적중 기준선 |

> **대조군이 해석을 뒤집은 사례.** 유흥주점 `비어(바)살롱`의 상호에 노래 키워드가 52.6%
> 나와 처음에는 오분류 신호로 읽었다. 그러나 음성 대조로 둔 `룸살롱`도 **44.5%**였다.
> 유흥주점은 13개 업태 전반이 노래주점 형태로 운영돼 노래 키워드에 변별력이 없다. 대조군을
> 재지 않았으면 틀린 근거를 기록할 뻔했다.

## 5-2. `NEEDS_REVIEW` 상호 표본 조사

건수 상위 3개 업태를 조사했다. 표본이 아니라 **모집단 전량**에 상호 키워드 규칙을 적용해
표본 오차를 없앴다. [측정: 2026-08-22 부울경 영업중 전량. 프랜차이즈 브랜드명 포함]

| 업태 | 건수 | 상호로 분류됨 | 주요 분포 |
| --- | ---: | ---: | --- |
| 일반음식점 `기타` | 14,047 | 38.0% | 카페 13.5% · 한식 7.5% · 주점 6.9% · 양식 5.6% · 분식 3.5% |
| 휴게음식점 `기타 휴게음식점` | 5,357 | 53.7% | 카페 21.3% · 분식 12.1% · **PC방 8.6%** · **편의점 8.1%** |
| 일반음식점 `경양식` | 5,269 | 35.7% | 양식 21.7% · 카페 7.2% · 주점 2.7% · 한식 2.2% |

**정확도는 높고 재현율이 낮다.** 분류된 건은 버킷별 12건 육안 검수에서 거의 전부 맞았다
(편의점·PC방·한식·주점은 12/12). 반면 미분류가 46~64%로 남는다. 프랜차이즈 브랜드 26종을
추가해도 1.5~3.3%p만 회수됐고, 남은 미분류는 `히키코모리`·`광평`·`시그널`·`그집`처럼
**상호에 업종 정보가 아예 없는 고유명사**다. 규칙을 더 늘려도 크게 줄지 않는다.

### 분리 가능한 것과 계속 미확정인 것

**분리 가능** — 상호 신호가 강하고 오분류 위험이 낮다.

| 대상 | 건수 | 갈 곳 |
| --- | ---: | --- |
| 휴게음식점 `기타`의 편의점 | 434 | `SHOP` / `CONVENIENCE_STORE`. 브랜드명(GS25·CU·세븐일레븐)이라 오분류 위험이 가장 낮다 |
| 휴게음식점 `기타`의 PC방 | 460 | **대응 subtype 없음.** 아래 참고 |
| 휴게음식점 `기타`의 카페 | 1,140 | `CAFE` / `GENERAL_CAFE` |
| 일반음식점 `기타`의 카페 | 1,891 | `CAFE` — PlaceType이 RESTAURANT가 아니다 |

**계속 미확정** — 근거가 부족하다.

- 세 업태의 미분류 잔여 **14,580건**. 상호에 정보가 없어 추가 원천 없이는 못 가른다.
- 일반음식점 `경양식` 전체. 양식 지지가 21.7%뿐이라 나머지 78%를 `WESTERN`으로 적재할
  근거가 없다. **`target` 컬럼을 비웠다.**
- 일반음식점 `기타` 전체. 카페 13.5%가 섞여 **PlaceType조차 단정할 수 없다.** `target`을 비웠다.

`NEEDS_REVIEW`이면서 `target`이 빈 건수는 **33,559건**이다.

### 상호 기반 분리는 다른 층이다

위 "분리 가능"을 `license_subtypes.csv`에 바로 넣지 않았다. 이 파일의 키는
`(업종, 업태구분명)`이고 값은 **원천이 준 분류**다. 상호에서 업종을 추론하는 것은 원천 사실이
아니라 우리의 해석이므로 층이 다르다. 규칙 층을 새로 두는 것은 설계 결정이라 측정만 남긴다.

### PC방 — 대응 subtype이 없고 전용 원천이 따로 있다

휴게음식점에 PC방으로 잡힌 460건은 `PlaceSubtypeCode` 64개 중 어디에도 없다. 별도 원천
`문화_인터넷컴퓨터게임시설제공업`이 부울경 영업중 **2,454건** 있으며, 460건은 음식 판매를
겸해 양쪽에 등록된 것일 수 있다. **중복은 측정하지 않았다.** PC방을 서비스에 노출할지는
제품 결정이다.
