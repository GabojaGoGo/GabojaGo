# `PlaceSubtypeCode` 기준 장소 원천 적재 계획

서비스 화면의 출시 순서가 아니라, Java
`PlaceSubtypeCode`에 정의된 장소를 운영할 수 있도록 **원천을 먼저 전부 적재하고
정제한다.** TourAPI는 여러 원천 중 하나이며, 장소와 `PlaceInfo`의 기본 원천으로
고정하지 않는다. 필드별로 가장 신뢰도 높은 원천을 선택한다.

- 기준일: 2026-08-09
- data-import 내부 처리 경로: 원본 API/CSV → 원천별 staging → `Place` 후보 매칭 → `PlaceInfo`
  원문 저장 → 검수 → `PlaceAttribute` 파생. 이 경로가 적용되는 프로젝트 실행 단계와 진입 게이트는 `L0` 6절이 소유한다.
- `Info`는 원천 사실이고, `Attribute`는 정제·판단 결과다.
- 원천의 필드가 존재해도 자동으로 `PlaceInfo`에 넣지 않는다. Java `InfoKey`에
  매핑을 정의한 필드만 넣고, 그 전에는 staging 원본으로 보존한다.

## 0. 현재 원천 탐색(`GO-125`)의 목적

**이 절이 `GO-125`의 작업 목적을 소유한다.** 아래 원칙을 다른 문서에 복사하지 않고 여기로
링크한다. 원칙이 바뀌면 여기만 고친다.

### 목적은 `AttributeKey`의 빈칸을 채우는 것이 아니다

`GO-125`는 `attribute_sources.csv`에서 `SOURCE_SEARCH_PENDING`인 조합을 계기로 열렸지만,
**그 칸을 채우는 것이 목적이 아니다.** `AttributeKey` 체계는 아직 최종 확정 전이므로
(`L0` 2-2절 — 34개는 상한이 아니다), **특정 키의 채움률이 0%라는 사실을 원천 탐색의
우선순위 근거로 쓰지 않는다.** 아직 확정되지 않은 목표에 맞춰 탐색 순서를 정하면, 나중에
키가 바뀔 때 그 탐색이 통째로 헛일이 된다.

지금 확보해야 하는 것은 **staging·`Info` 후보로 보존할 가치가 있는 원천 사실**이다.
보존은 지금 해야 싸고, 해석은 나중에 해도 된다(`L0` 4절 `원천 저장 범위`).

### 탐색 단위와 진행 순서

`GO-125`는 특정 API를 승인받아 쓰는 작업이 아니다. 탐색 단위는 원천 하나가 아니라
**`PlaceType` × 확인할 원천 사실**이다. 어떤 사실을 어느 `PlaceType`에서 확인할지 먼저 정하고,
그 사실을 줄 수 있는 후보를 찾는다.

현재 `PlaceType`은 P1 원천 탐색을 위한 대분류 기준이다. 원천이나 장소군이 현재
`PlaceType`에 애매하게 걸치거나 자연스럽게 들어가지 않아도 탐색·실측·원본 보존은 계속한다.
P1에서 새 `PlaceType`·`PlaceSubtype`을 임의로 확정하지 않으며, 후보·관찰사항·미결 사유로
기록해 P2-A 검토사항으로 넘긴다. **분류가 애매하다는 이유만으로 원천 탐색 대상에서 제외하지
않는다.**

어떤 사실을 고를지는 추천이 실패할 수 있는 지점에서 출발하지만, **그것은 탐색을 여는 계기이고
우선순위 근거가 아니다.** 추천 실패 조건 자체를 정의하는 것은 P2-B다(`L0` 6절).

각 원천 사실마다 [`L0` 4절](../../docs/L0-project-context.md) `원천 부재 판정`의 **다섯 범위**를
빠르게 훑는다. 범위 목록은 `L0`이 소유하며 여기서 다시 정의하지 않는다.

이 단계에서는 범위마다 아래 셋까지만 확인하고 멈춘다.

```text
1. 후보가 있는가        없으면 없다고 기록한다
2. 무슨 사실을 주는가    명세 수준으로 충분하다
3. 기본 이용조건        무료·저장·재배포 허용 여부
```

채움률·값 분포·연결률은 여기서 재지 않는다. 다섯 범위를 다 훑기 전에 한 후보를 파고들면
탐색이 그 후보의 승인 절차와 문서에 묶인다.

그다음 가치가 높은 **2~3개만 shortlist**로 올린다. 비교 기준은 다섯이며, 앞의 넷은 아래
`원천을 볼 때 재는 것`의 7항목과 같은 축이므로 따로 정의하지 않는다.

```text
모집단·순증 · 필드 품질 · 최신성과 변경 감지 가능성 · 기존 장소 연결 가능성
이용·저장·재배포 조건    7항목에 없던 축. 무료가 아니면 후보에서 제외한다(`L0` 5절 `예산`)
```

원천 형식이 CSV인지 API인지는 그 자체로 우선순위 기준이 아니다. 각 사실의 변경 빈도와 원천의
실제 갱신 주기·제공 시점·접근 조건을 비교해 적합성을 판단한다. 비교적 안정적인 사실은 정기 CSV
스냅샷으로도 충분할 수 있지만, 영업시간·메뉴·가격·예약·실시간 운영정보처럼 자주 바뀌는 사실은
최신 API 또는 반복 수집이 필요한 후보로 본다.

API라는 이유만으로 최신성·품질을 가정하거나 자동 채택하지 않는다. 실제 갱신 주기와 값의
최신성을 확인하고 저장·재배포·상업 이용 조건과 비용도 함께 본다. P1에서는 각 원천에 적합한
수집 방식을 관찰·기록하는 데 그치며, 최종 수집·갱신 구조는 P3에서 결정한다.

**승인은 탐색의 시작 조건이 아니다.** API 키 발급·활용신청·토큰 발급·제휴 계약을 먼저
해결하려고 하면, 다섯 범위를 훑기도 전에 탐색이 한 포털의 승인 대기열에 갇힌다. 신청 시점과
그 예외는 [`L0` 4절](../../docs/L0-project-context.md) `실측 범위`가 소유한다.

### 원천을 볼 때 재는 것

`AttributeKey`에 대응하는지를 먼저 묻지 않는다. 원천이 실제로 무엇을 주는지를 먼저 잰다.

```text
1. 실제로 제공하는 원본 필드     명세가 아니라 응답·파일에 있는 것
2. 채움률                      컬럼 존재는 근거가 아니다
3. 값 분포                     한쪽으로 몰리면 채워져 있어도 변별력이 없다
4. 값의 단위·의미               같은 컬럼에 다른 단위가 섞일 수 있다
5. 연결성                      기존 장소와 이름·주소·좌표로 이어지는가
6. 모집단 범위                  부울경에서 몇 건이며 기존 base의 몇 %를 덮는가
7. 기존 원천 대비 순증 가치       이미 있는 것과 겹치면 새로 얻는 게 없다
```

3·4번을 건너뛰면 채움률만 보고 쓸 수 없는 값을 채택하게 된다. 산림청 등산로 소요시간
(집계 단위 불일치)과 전국관광지정보표준데이터 `수용인원수`(지자체별 단위 혼재)가 둘 다
채움률 97% 이상이면서 부적합했다. 근거는
[`attribute-coverage.md`](attribute-coverage.md)의 `측정했으나 채택하지 않은 것`에 있다.

### 이 단계에서 하지 않는 것

아래는 전부 **후속 단계**다. `GO-125`에서 결론 내지 않는다.

- 원천 필드를 `AttributeKey`에 매핑하는 것
- 새 `AttributeKey`를 추가하는 것
- `Attribute` 파생·등급화 규칙을 확정하는 것

측정 결과는 `attribute_sources.csv`의 `measured_*` 컬럼과
[`attribute-coverage.md`](attribute-coverage.md)에 근거로 남기되, `status`를 옮기는 것은
그 키의 성격이 확정된 뒤에 한다. 판정 절차는
[`classification-mapping.md`](classification-mapping.md) 5절이 소유한다.

### 탐색 종료 조건

아래 셋이 모두 충족되면 그 원천 사실의 탐색은 끝난 것으로 본다. 더 찾지 않는다.

```text
1. 다섯 범위 각각에서 후보 유무 또는 미조사 사유가 기록됐다
2. 즉시 실측할 후보 2~3개, 또는 후보 부재 근거가 정리됐다
3. 각 후보의 다음 행동이 원본 확보 / 승인 신청 / 약관 검토 / 제외 중 하나로 결정됐다
```

3번이 남아 있으면 탐색이 아니라 대기다. 어느 것도 고를 수 없다면 고를 수 없는 이유를
기록하는 것까지가 탐색이다.

### A/B표를 읽는 방법

아래 1절의 A/B 후보표는 **탐색 후보 목록이지 요구사항이 아니다.** 어떤 후보에 붙은
"`X`·`Y` 키가 걸려 있다"는 메모는 그 원천을 왜 찾았는지에 대한 기록일 뿐이며, **그 키를
반드시 채워야 한다는 뜻이 아니다.** 원천을 재본 결과 그 키에 안 맞으면 그것으로 측정은
성공한 것이고, 다른 원천 사실이 보존할 가치가 있으면 그쪽을 남긴다.

## 1. TourAPI의 역할 — 전체 기준선이 아니라 관광 콘텐츠 원천

TourAPI는 `ACCOMMODATION`, `ACTIVITY`, `CAFE`, `RESTAURANT`, `SHOP`,
`TOURIST_SPOT`의 넓은 subtype 범위를 제공한다. 특히 `ACTIVITY`와 관광지의
설명·이미지·반복 정보는 현재 다른 도입 원천으로 대체하지 않는다. 그러나
인허가 상태, 업종 분류, 시장·주차장·축제의 행정 사실은 해당 공공 원천을 먼저
쓴다.

| subtype 군 | TourAPI에서 먼저 보존할 Info |
| --- | --- |
| 숙소 | 체크인/아웃, 객실 유형·수, 취사 가능 여부, 주차 |
| 카페·음식점·술집 | 영업시간, 휴무일, 대표·전체 메뉴, 포장, 주차 |
| 상점·시장 | 영업시간, 휴무일, 판매품, 화장실, 주차 |
| 관광지·축제·공연 | 행사 시작·종료일, 장소, 주최, 관람시간, 입장료, 프로그램 |
| 액티비티 | 영업시간, 주차, 이용요금·예약 관련 원문 |

TourAPI에서 시작할 필요는 없다. 모든 원천을 독립적으로 staging에 쌓고, 이름·
정규화 주소·좌표로 같은 장소를 연결한다. TourAPI `contentid`는 연결된 장소의
추가 원천 키로만 보관한다.

### 사실별 원천 선택

원천 전체의 우열을 매기지 않는다. 사실마다 따로 정한다. 한 원천이 모든 사실을 잘
주지는 않는다.

판단 기준은 네 가지다.

| 기준 | 묻는 것 |
| --- | --- |
| 권위성 | 그 사실을 공식적으로 관리하는 원천인가 |
| 완전성 | 부울경에서 필요한 필드가 실제로 얼마나 채워지는가 |
| 연결성 | 안정적인 원본 ID·주소·좌표로 기존 장소와 연결되는가 |
| 최신성 | 변경·폐업·삭제를 신뢰성 있게 추적할 수 있는가 |

네 기준을 합쳐 종합점수를 만들지 않는다. 사실마다 지배하는 기준이 다르다.
**해당 사실의 핵심 기준을 충족하지 못한 원천은 다른 장점이 있어도 그 사실의 원천으로
채택하지 않는다.** 관광 설명이 풍부해도 폐업 추적이 부정확하면 영업 상태 원천으로는
탈락이다.

좌표는 값 자체가 틀릴 수 있으므로 정확성을 따로 검증한다. 채워져 있고 매칭이 되어도
수백 미터 어긋날 수 있다. 정확성은 정답을 알 수 있는 필드에만 적용하는 보조 기준이다.

아래는 현재 후보와 채택 상태다. **실측 전 원천은 채택이 아니다.** 측정값은 Jira에
남기고 이 표에는 결론만 반영한다.

| 사실 | 핵심 기준 | 우선 후보 | 보조 후보 | 상태 | 근거 |
| --- | --- | --- | --- | --- | --- |
| 인허가·영업 상태·인허가일 | 권위성·최신성 | 행정안전부 식품·문화 인허가 | 없음 | **부분 실측** — 권위성·완전성·연결성 확인, 음식점·카페·술집·숙소의 base로 잠정 사용. **핵심 기준인 최신성 미검증이므로 채택 아님** | `GO-120` `GO-123` |
| 상권업종 세분류·층/호 | 완전성·연결성 | 소상공인시장진흥공단 상가정보 | 없음 | **부분 실측** — 부울경 387,313건, 주소·좌표 100%, WGS84. SHOP base로 잠정 사용. **상가업소번호 안정성·중복률 미측정** | `GO-120` |
| 주차장 운영시간·요금·구획수 | 완전성·최신성 | 전국주차장정보표준데이터 | 없음 | **실측 완료** — 부울경 2,529건, 운영시간·요금 채움률 100%, WGS84 | `GO-79` |
| 시장 개설주기·시장 편의 정보 | 권위성·완전성 | 전국전통시장표준데이터 | TourAPI 쇼핑 정보 | **실측 완료** — 부울경 356건, TourAPI 쇼핑(38) 대비 이름 일치 19.7%(신규 80.3%, 좌표검증 500m 이내 100%). **핵심 기준인 최신성 미검증이므로 채택 아님** | `GO-80` `GO-125` |
| 축제 기간·개최장소·주최 | 권위성·최신성 | 전국문화축제표준데이터 | TourAPI 행사 정보 | **실측 완료** — 부울경 182건 중 73.1%가 이미 종료일 경과. **핵심 기준인 최신성 탈락, 채택 아님** | `GO-81` `GO-125` |

| 대표 이미지 URL | 완전성 | TourAPI | 없음 | 미실측 — 목록 응답에 `firstimage` 존재만 확인 | `GO-73` |
| 좌표 | 연결성·정확성 | 미정 | 미정 | **부분 실측** — 주차장 WGS84, 식품 인허가 EPSG:5174 계열. 상가정보 미확인 | `GO-79` `GO-120` `GO-94` |

`상태` 칸에는 결론과 함께 **무엇을 어디까지 쟀는지**를 적는다. 범위 없이 결론만 적으면
측정한 것보다 넓게 단정한 것을 알아챌 수 없다. 자세한 규칙은
[`L-1-operating-principles.md`](../../docs/L-1-operating-principles.md) 6절에 있다.

**`base로 잠정 사용`과 `채택`은 다르다.** base는 어느 원천으로 `Place`를 만들지 정한 것이고,
채택은 그 사실의 정본으로 확정한 것이다. base는 다른 원천이 더 나은 것으로 확인되면 바꿀 수 있다.
채택은 네 기준을 모두 통과해야 하며, 특히 **해당 사실의 핵심 기준을 재지 않은 원천은 채택하지 않는다.**

`미실측`은 아직 재보지 않았다는 뜻이고, 원천이 그 사실을 아예 제공하지 않는 경우는
`해당 없음`으로 적는다. 둘은 다르다. 미실측은 언젠가 재야 하고 해당 없음은 재지 않는다.

최신성은 한 번 수집해서는 잴 수 없다. 표본 단계에서는 갱신 필드(기준일·갱신시점)의
존재 여부까지만 확인하고, 실제 변경 감지율은 재수집 이후에 채운다.

### PlaceType별 후보 원천 관리

모집단 후보는 **PlaceType별로** 관리한다. 현재 채택 원천을 실측·적재하는 동안 다른
공식 CSV·API 후보를 조사해 대기열에 넣고, 원본을 확보하면 같은 부울경 범위와 기준일로
비교한다. 후보가 더 좋은 근거를 내면 현재 채택 원천도 바꿀 수 있다.

다만 최종 병합에서는 원천 전체를 한꺼번에 우열화하지 않는다. PlaceType 후보를 실측한
뒤, 실제로 채택할 값은 위의 **사실별 원천 선택** 원칙으로 결정한다. 따라서 어떤 후보는
모집단 전체를 대체하고, 어떤 후보는 빠진 subtype이나 운영 정보만 보강할 수 있다.

| 상태 | 의미 |
| --- | --- |
| 탐색 | 구체적인 원천을 더 찾아야 함 |
| 문서 확인 | 운영기관·제공 필드·접근 및 이용조건만 확인함. 품질은 미검증 |
| 원본 확보 대기 | 실측할 API·CSV가 정해졌지만 아직 원본을 받거나 호출하지 않음 |
| 실측 중 | 실제 원본으로 건수·채움률·연결률 등을 측정 중 |
| 채택 | 핵심 기준을 통과해 현재 우선 원천으로 사용함 |
| 보조 채택 | 우선 원천의 값이 없거나 유효하지 않을 때만 사용함 |
| 탈락 | 해당 사실의 핵심 기준을 통과하지 못함. 원천 전체의 탈락은 아님 |

인터넷·포털 조사만으로 올릴 수 있는 최고 상태는 `문서 확인`이다. `채택`과
`보조 채택`은 실제 원본 실측 근거가 있을 때만 사용한다.

## 2. 현재 기준선 수집 운영

후보 목록은 1절에서만 관리한다. 이 절에는 현재 기준선으로 사용 중인 원천의 수집 방식만
남긴다. `PARKING_LOT`은 `PlaceSubtypeCode`가 아니라 독립 `PlaceType`으로 운영한다.

**`MNG_NO`를 단독 식별자로 쓰지 않는다.** 실측에서 `관리번호`가 자치단체를 넘어 중복됐다

행정안전부 세 API는 모두 `serviceKey`, `pageNo`, `numOfRows`(최대 100)가
필수다. `CRD_INFO_X/Y`는 WGS84가 아니라 EPSG:5174이므로, 변환 검증 전에는
지도 좌표로 사용하지 않는다.

### CSV 다운로드 규칙

1. 각 데이터셋 페이지에서 원본 CSV를 내려받는다.
2. 원본 파일은 `data-import`의 입력 보관 위치에 파일명·데이터기준일자·다운로드
   시각과 함께 보존한다.
3. 주차장은 `주차장관리번호`, 시장은 제공되는 이름·주소·좌표, 축제는 이름·기간·
   개최장소를 staging의 중복 판정 재료로 쓴다.
4. CSV를 DB에 바로 덮어쓰지 않는다. 새 파일의 레코드를 staging에서 비교하고
   장소 매칭·값 정제 결과만 본 테이블에 반영한다.

## 3. subtype별 반영 원칙

위 대기열에서 원본 실측을 통과한 후보만 현재 모집단에 합치거나 보강 원천으로 쓴다.
특히 단란·유흥주점, 관광펜션·도시민박·한옥체험, 공원·야영장·유원시설처럼 현재
모집단에서 빠질 수 있는 subtype은 **현재 원천과의 중복률·신규 비율을 먼저 측정**한다.

새 원천 레코드는 기존 staging 전체를 이름·정규화 주소·좌표 거리로 먼저 찾는다.
매칭이 확실하지 않으면 자동 병합하지 않고, 새 후보로 남긴다. 후보가 많다는 이유만으로
현재 모집단에 모두 합치지 않는다.

### 분류 축 확장 — 원천 보존이 전제다

`PlaceSubtypeCode`(64개)와 `AttributeKey`(34개)의 현재 개수는 상한이 아니다. 원천을 더
저장할수록 축을 세분화할 수 있고, **그때 필요한 재료는 지금 버리지 않은 원본뿐이다.**
확장 자체는 실제 추천 질의가 그 구분을 요구할 때 하지만, 보존은 지금 해야 한다. 판단 규칙은
[`L0` 4절](../../docs/L0-project-context.md)의 `분류 축의 확장 조건`·`원천 저장 범위`를 따른다.

| 농어촌민박 4,823 · 관광펜션 209 · 도시민박 1,314 · 한옥체험 119 | `PENSION_HOMESTAY` · `GUESTHOUSE_HOSTEL` · `HANOK_STAY` | 법적 근거가 다른 4종이 3개 값에 겹쳐 들어간다 |
| 테마파크 기타 417 · 일반 64 · 종합 6 | `THEME_PARK` 1개 | 규모 차이가 사라진다 |

`AttributeKey`도 같다. 주차장 표준데이터로 계산한 **근접 공영주차장 존재율**은
`PARKING_CONVENIENCE`("이 장소에 주차장이 있다")와 다른 사실이라 넣지 못했고, 지금은 담을
키가 없다. 농어촌민박업의 `객실수`(채움률 98.5%)도 마찬가지로 `InfoKey` 후보만 있고 대응
`AttributeKey`가 없다.

배정 규칙과 확장 판정 절차는 [`classification-mapping.md`](classification-mapping.md)가 소유한다.

**이 표는 지금 축을 늘리자는 제안이 아니다.** 늘릴 근거가 생겼을 때 무엇을 쪼갤 수 있는지
기록해 둔 것이며, 그 선택지를 살려두는 조건이 원본 보존이다. `업태구분명`처럼 현재
`InfoKey`에 매핑이 없는 컬럼도 staging에서 지우지 않는다 — 위 구분을 나중에 만들 수 있는
유일한 재료다.

## 4. `PlaceInfo` 반영 전 세부 계약

이 절은 L0의 P2-C 계약을 data-import 관점에서 구체화한다. 구현 착수 여부와 프로젝트 전체 순서는 이 문서가 정하지 않는다.

현재 `InfoKey` 설계는 TourAPI 중심이다. 외부 원천을 실제 `PlaceInfo`로 옮기기
전에 다음 키·병합 규칙을 Java에 먼저 확정한다.

| 외부 원천 사실 | `InfoKey` 후보 | 적용 subtype |
| --- | --- | --- |
| 인허가/영업 상태, 인허가일 | `LICENSE_STATUS`, `LICENSE_DATE` | 음식점·숙소 |
| 객실수, 한실수, 양실수 | `ROOM_COUNT`, `ROOM_TYPE` | 숙소 |
| 시장 개설 주기 | `MARKET_DAY` | 전통시장·정기시장 |
| 화장실/주차장 보유 | `RESTROOM`, `PARKING_INFO` | 시장 |
| 주차장 운영시간·요금·구획수 | `OPERATING_HOURS`, `PARKING_FEE`, `PARKING_CAPACITY` | 주차장 |
| 축제 기간·장소·주최 | `EVENT_START_DATE`, `EVENT_END_DATE`, `EVENT_PLACE`, `ORGANIZER` | 축제 |

`InfoKey`를 먼저 정의하지 않은 원천 필드는 삭제하지 않고 staging 원본으로
보존한다. 키·병합 우선순위·값 정규화 규칙이 확정된 뒤에 `PlaceInfo` upsert를
수행한다.

### 원천 식별 규칙 — `Place.sourceType`

`Place.sourceType`은 유지한다. 재수집 시 덮어써도 되는 레코드와 보존해야 하는
레코드를 구분하는 유일한 근거이기 때문이다. `CURATED`로 직접 등록한 장소를
공공 원천 재수집이 덮어쓰면 손으로 넣은 데이터가 사라진다.

현재 `PlaceDataSourceType`은 `TOUR_API`, `CURATED` 두 값뿐이라 이 문서가 적재
대상으로 정한 보강 원천을 받을 수 없다. 원천별 staging을 `Place`로 승격하기
전에 다음 값을 먼저 정의한다.

| 원천 | `PlaceDataSourceType` 후보 |
| --- | --- |
| TourAPI | `TOUR_API` |
| 전국주차장정보표준데이터 | `PARKING_STANDARD` |
| 행정안전부 식품(일반음식점) | `FOOD_LICENSE` |
| 소상공인시장진흥공단 상가(상권)정보 | `COMMERCIAL_DISTRICT` |
| 행정안전부 문화(숙박업) | `LODGING_LICENSE` |
| 행정안전부 문화(관광숙박업) | `TOURIST_LODGING_LICENSE` |
| 전국전통시장표준데이터 | `TRADITIONAL_MARKET_STANDARD` |
| 전국문화축제표준데이터 | `CULTURAL_FESTIVAL_STANDARD` |
| 직접 등록 | `CURATED` |

원천이 준 관리번호·상가업소번호 등 원본 식별자는 `Place.sourcePlaceId`에
보존한다. `sourceType`과 `sourcePlaceId`는 함께 있어야 증분 갱신 시 같은
레코드를 다시 찾을 수 있다.

`sourceType`과 `sourcePlaceId`는 모두 운영용 내부 필드이므로 API 응답에는
노출하지 않는다.

## 7. 단일 원천 적재 검증에 필요한 data-import 조건

이 조건은 L0의 P4 단일 원천 검증에서 data-import가 충족할 세부 조건이다. 프로젝트 단계 전환을 이 문서에서 판정하지 않는다.

1. 각 API/CSV 원본이 staging에 원천 식별자와 갱신시점으로 보존돼 있다.
2. subtype별로 TourAPI 장소와 외부 원천의 매칭/미매칭/충돌 수를 집계했다.
3. Java `InfoKey` 매핑과 원천별 병합 우선순위가 확정돼 있다.
4. `PlaceInfo`에 원문을 upsert한 뒤, 빈값·형식 오류·중복을 검증했다.
5. 그 후에만 Info → Attribute → Purpose 정제를 실행한다.

### 8-2. 여러 원천에서 재현된 공통 규칙

1. **인허가 계열 원본 식별자는 `관리번호` 단독으로 고유하지 않다.**
   `(개방자치단체코드, 관리번호)` 조합이어야 한다. 박물관 146건의 `관리번호` 고유값이 116,
   전통사찰 372건이 235, `ACTIVITY` 레저 묶음 2,035건이 609였고, 조합으로는 셋 다 1:1이 된다.
   다만 **업종에 따라 다르다** — `생활_대규모점포`는 617건의 `관리번호`가 조합 없이도 617개로
   고유했다. 따라서 "LOCALDATA는 항상 중복"이 아니라 **`관리번호` 단독 고유를 전제하지 않고
   조합 키를 기본으로 쓴다**가 규칙이다. 2절 `원본 식별자` 표는 이 규칙에 맞춰
   `(개방자치단체코드, MNG_NO)`로 갱신했다.
2. **TourAPI 부울경 집계는 `areacode`가 아니라 주소로 한다.**
   목록 응답의 `areacode` 채움률이 48.0%다(문화시설 전국 2,713건 기준). `addr1`은 100%다.
   문화시설 부울경이 `areacode` 기준 152건, 주소 기준 349건으로 2.3배 차이가 났다.
3. **장소 이름 매칭에서 괄호를 지우지 않는다.**
   TourAPI `title`의 괄호는 지역 표기다(`관음사(창녕)`). 지우면 동명 장소가 오매칭된다.
   `이름 + 시도 + 시군구`를 함께 요구한다. 전통사찰에서 이름만 비교하면 233건이 맞았으나
   시군구를 요구하면 206건으로, 27건이 과대계상이었다.
   주소 괄호 규칙(지번=층, 도로명=법정동)은 1절이 소유하며 이것과 별개다.
4. 인허가 계열 좌표는 **EPSG:5174 계열 투영좌표**다. 박물관·전통사찰에서 재확인했다.

`gis-heritage.go.kr`의 검색·다운로드 API를 재현해 **로그인·서비스키 없이** 부울경 필터
ZIP(shapefile 6종)을 직접 받았다. 절차는 `POST /newHeritageDownload.do`(시도 코드로 검색)
→ `GET /board/heritageDownload/downloadFilesAll2.do?sidoList=ADDR260000,ADDR310000,ADDR480000&tab=1&...`
(필터링된 전체 결과를 즉시 blob으로 응답)이다. 시도 코드는 검색 페이지 HTML에 하드코딩돼
있다(부산 260000·울산 310000·경남 480000).

받은 유산 레코드(보호구역 레이어 제외) **1,353건** — 국가지정유산 223(국보10·보물82·
사적71·천연기념물33·명승18 등) · 시도지정유산 1,048 · 국가등록문화유산 80 ·
시도등록문화유산 2. **geometry가 점이 아니라 폴리곤**(EPSG:5179, UTM-K)이고, dbf
속성에는 시군구명까지만 있어 상세 주소·좌표는 대표점 계산을 거쳐야 얻을 수 있다. 공공누리
(KOGL) 표시가 있으나 구체 유형(1~4)은 미확인이라 상업적 이용 가능 여부를 아직 단정할 수
없다. 상세는 1절 A표와 `source-downloads.md`, `data/reports/heritage-spatial-info-20260824-0650Z.json`.

**이 다운로드 경로를 찾은 방법 자체가 재사용 가능한 패턴이다.** data.go.kr 카탈로그의
"기관자체에서 다운로드" 표기는 승인이 필요하다는 뜻이 아니라 **다운로드 로직이 그 기관
사이트에 있다는 뜻일 뿐**이었다. 기관 웹사이트의 다운로드 버튼이 호출하는 JS를 읽으면
그 안에 실제 엔드포인트와 파라미터가 그대로 있는 경우가 있다.

### 부산 Big-데이터웨이브 — 검색 API 재현, PlaceType별 후보 확인

포털은 의미 기반(임베딩 벡터) 검색을 쓰는 SPA다. 브라우저로 실제 사용된 엔드포인트

"관광지"(29건)·"숙박"(66건)·"체육시설"(66건) 검색으로 확인한 것은 두 갈래다.

## 13. GO-125 세션 재개 — 국가유산청 완결 측정 + 부산/경남 신규 후보 4종 실측 (2026-08-24)

### 국가유산청 — 대표점 계산·좌표 변환·TourAPI 연결성 완료

`pyproj`를 로컬 venv에만 설치해(프로젝트 의존성에는 추가하지 않음) 폴리곤 대표점(최대 링

### 부산 포털 파일 다운로드 링크를 찾는 재사용 가능한 방법

상세 모달의 다운로드 버튼을 클릭해도 `read_page`에 실제 파일 링크가 안 잡히는 경우가

파일은 예외 없이 **data.go.kr 공용 엔드포인트**(`fileDownload.do?atchFileId=…`)로
서빙되며 이 엔드포인트는 세션·서비스키 없이 단순 GET으로 응답한다 — 10절에서 확인한

## 14. GO-125 세션 재개 — 부산/울산/경남 PlaceType별 폭넓은 탐색 (2026-08-24, 4차)

13절 완결 작업 이후 정밀 검증을 멈추고 **아직 못 찾은 원천을 넓게 찾는 데** 집중했다.
부산·경남·울산 포털에서 문화시설·공원·체육·숙박·체험 키워드로 추가 검색하고, 국가유산청
외 전문기관(한국산림복지진흥원, 울산·경남 관광재단)을 확인했다.

### 부산 — 해수욕장·공원·공공미술 신규 확인

"해수욕장" 검색으로 [부산광역시_해수욕장 방문 현황](https://data.busan.go.kr/bdip/opendata/dataSet.do)을
받아 실측했다. 7개 해수욕장(연도별 반복 통계)인데 TourAPI 관광지(12)에 6/7이 이미 있어
**장소 원천으로는 순증이 없다** — 송도해수욕장 1곳만 신규. "공원" 검색에서
[부산시설공단_공원시설 현황 조회 서비스](https://data.busan.go.kr/bdip/opendata/dataSet.do)
(시민공원·중앙공원·태종대유원지 등, API 활용신청 21건)를, "문화시설" 검색에서
[부산광역시_공공미술 현황](https://data.busan.go.kr/bdip/opendata/dataSet.do)(활용신청 42건)을
확인했다 — 둘 다 API 이용신청이 필요해 **접근 대기**로 기록했다. "문화시설" 검색에서 발견한
[부산교통공사_도시철도 역세권정보](https://data.busan.go.kr/bdip/opendata/dataSet.do)는
태그상 이미 확보한 "역세권 관광지 현황"(91건)보다 넓은 역세권 종합 POI로 추정되나
원본은 아직 확인하지 않았다.

### 경남 — 시군별 공공체육시설·숙박업 다수 확인, 개별 다운로드는 보류

특히 [경상남도 함양군_공공문화체육시설현황도](https://bigdata.gyeongnam.go.kr/)는
도서관·공연장·체육관·운동장·체육공원을 아우르는 **다분류 GIS(shp/dbf/shx) 파일**이라
다른 시군보다 정보 밀도가 높아 보인다. "숙박업" 검색 15건도 대부분 시군별 개별
배포였다(산청군·창녕군·진주시·남해군 등) — 부산 사례로 볼 때 LOCALDATA 재배포일 가능성이

다운로드가 필요하다** — 이번 세션에서는 개별 다운로드·실측을 보류하고 존재만 기록한다.

### 울산 — 대공원 세부시설 정보 위주, 새 모집단 없음

"공원" 검색 결과는 대부분 **울산대공원 하나**의 하위 시설 정보(수영장 수질, 휴무일,

[전국추모공원정보표준데이터](https://www.data.go.kr/)를 새로 확인했으나(울산시설공단
제공) 추모공원은 현재 서비스 성격과 거리가 멀어 낮은 우선순위로만 기록한다.

### 전문기관 — 한국산림복지진흥원, 지역 관광재단

[한국산림복지진흥원_소속기관정보](https://www.data.go.kr/data/15061976/fileData.do)는
전국 16행(소속기관 단위, 개별 시설이 아님)뿐이라 규모가 매우 작다 — 문서 확인 수준으로만
기록하고 다운로드하지 않았다. 울산문화관광재단·경남관광재단의 음식관광 API(redtable.global

기록했다.

**측정하지 않은 것** — 부산 공원시설·공공미술 API 승인 후 실측 · 부산 역세권정보(넓은 버전)
원본 확인 · 경남 시군별 체육시설·숙박업 18곳 개별 다운로드·LOCALDATA 대조 · 울산문화관광재단·
경남관광재단 토큰 발급 후 실측(현재 대기 유지, 임의 진행 안 함).

확장이 아니라 대표메뉴·음식종류 등 큐레이션 필드 보강 목적으로 가치가 크다.**

## 16. GO-125 세션 재개 — 울산 공원·자연 계열 재탐색 + 경남 체육시설 유형 분류 확장 (2026-08-24, 7차)

## 18. GO-125 세션 재개 — 온누리상품권 가치 확인 + 새 독립 원천 2건 (2026-08-24, 9차)

반려동물 동반여행, 부산 관광기관 자체원천)은 문서 확인 단계에서 "엔드포인트 생존 여부
미확인" 또는 "기관·엔드포인트 자체가 미확인"으로 남아있던 항목들이다. 전부 **개별 지자체·
민간 큐레이션 API로, 정보 보강 성격이며 모집단 확장 후보가 아니다** — 지난 세션들에서 이미
같은 성격(부산 관광기관 자체 큐레이션, 서비스키 필요 가능성 높음)의 원천을 다수 확인한
뒤 남은 잔여 항목이라 termination 판단에 영향을 주는 "대형 미탐색 원천"으로 보지 않는다.

### 경남 A유형·B/D/E/F, PlaceType 공백 재확인

경남 A유형(공공체육시설 카탈로그)은 `§18`에서 7개 시군 순증 100% 확증 후 반복 실측을
중단한 상태를 유지한다. 이번 패스에서 추가 시군을 재확인하지 않았다. B(단일시설 이용통계)
·D(GIS/UPIS)·E(도 전체 등록체육시설 혼재)·F(API 승인 필요)도 새 자동 접근 가능 원천이
나오지 않아 그대로 둔다.

macro 수준에서 PlaceType 전체가 미탐색인 영역은 없다. `RESTAURANT`·`CAFE`·`BAR`·`SHOP`·
`ACCOMMODATION`·`TOURIST_SPOT`·`ACTIVITY`·`PARKING_LOT` 8개 PlaceType 전부 이번 세션
동안 최소 1개 이상의 확장 또는 정보 보강 후보를 실측했다. 분류 체계와 자연스럽게 맞지
않는 장소군(관광안내소·마리나·치유의숲·체험마을·도서관·공공미술·역세권 등)은 전부
`신규 장소군(관찰)`로 §1 표에 기록돼 있으며, 이 패스에서 새로 발견된 관찰군은 없다.

### GO-125 종료 권고

**종료를 권고한다.**

- 신규 고품질 원천 발견 빈도가 뚜렷이 감소했다(`§23`에서 이미 관찰). 이번 16차 패스는
  "아직 실제 미탐색 + 승인 불필요" 조건을 동시에 만족하는 마지막 후보(주차장개별정보)를
  실측했고 탈락으로 끝났다 — 같은 조건을 만족하는 후보가 더 남아있지 않다.
- 남은 후보는 전부 접근 대기(서비스키·활용신청)나 수동 접근 필요(CAPTCHA)로, 승인·계약
  판단이 필요한 P2/P3 영역이지 P1 탐색으로 더 진행할 수 있는 항목이 아니다.
- 8개 PlaceType 모두 최소 1건 이상 실측을 마쳤고, 분류 불일치 장소군은 전부 관찰사항으로
  기록됐다.
- 반대 근거("승인 없이 접근 가능한 명확한 미탐색 대형 원천")에 해당하는 항목은 이번
  패스에서 발견하지 못했다. 유일하게 남아있던 실측 가능 후보(주차정보)가 탈락으로
  확인되면서 이 근거가 소진됐다.

종료 여부의 최종 결정은 사용자 판단으로 남긴다.

## 25. GO-125 민간 대형 장소 원천 경쟁 후보 검토 (2026-08-24, 17차)

공공기관 원천만 비교해서는 GO-125 종료 판단이 불완전하다는 지적에 따라, Kakao Local·

민간 대형 원천을 경쟁 후보로 포함해도 `§24`의 종료 권고를 바꿀 근거는 나오지 않았다.

판단으로 남긴다.

**"B. 특정 장소군 보조 원천(제한적)"**로 재분류한다 — 공원(모집단 77.7%, 폴리곤

## 26. GO-125 경쟁 원천 비교 — 현재 확장 후보보다 나은 원천이 있는가 (2026-08-24, 19차)

접근 전제조건"이라고만 적었는데, 실제로 data.go.kr 심의유형을 확인한 결과 **둘 다

- **기상청_단기예보 조회서비스**(15084084) — 무료·자동승인. 날씨 영향 정보 보강용
- **한국교통안전공단_주차장실시간정보**(15150101) — 기존에 탈락시킨 `주차장개별정보`

- **한국관광공사 빅데이터 지역별 방문자수**(통신사 기반) — "실시간 혼잡도"에 가장

### 저장 가능성 vs 서비스 활용 가능성 재확인

기존 표의 `현재 미사용 이유`/`향후 재검토 조건` 구조가 이미 이 구분(P1 적재 부적합
≠ 서비스 전체 영구 제외)을 담고 있어 표 형식은 바꾸지 않았다. `decision-log.md`의
동일 원칙도 중복 기록하지 않았다.

### GO-125 종료 최종 판단

**종료를 권고한다.** 이번 감사로 새로 발견된 것은 전부 "존재는 확인했으나 실측은
P1 범위 밖"인 항목(공공 실시간 API 3건)이거나 "확인 결과 대표 후보가 이미 있어 추가
조사 불필요"(야놀자/여기어때)였다 — `§24`의 종료 권고를 뒤집을 근거는 나오지 않았다.
