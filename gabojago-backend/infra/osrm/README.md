# 영남권 OSRM 운영 안내

가보자GO는 부산·경남·울산을 포함하는 영남권 OSRM 그래프를 사용한다. 차량과 도보 그래프는 별도이며, 추천 API는 각 기준의 균형 루트를 하나씩 반환한다.

## 현재 구성

| 서비스 | OSRM 프로필 | 데이터 경로 |
| --- | --- | --- |
| `osrm` | `car.lua` / `driving` | `infra/osrm/yeongnam/car` |
| `osrm-foot` | `foot.lua` / `foot` | `infra/osrm/yeongnam/foot` |

현재 개발 환경에서는 두 서비스가 이미 구축·실행 중이다. 단순 재시작은 아래 명령이면 충분하다.

```bash
docker compose up -d osrm
docker compose --profile walking up -d osrm-foot
```

## 처음 구축하거나 데이터 갱신할 때

저장소 루트에서 실행한다. 스크립트는 전국 원본을 한 번 내려받은 뒤, 영남권 확장 경계(부산·경남·울산의 권역 경계 도로를 보존)만 추출해서 각 프로필을 만든다.

```bash
brew install osmium-tool # 최초 1회
chmod +x scripts/osrm-preprocess.sh

./scripts/osrm-preprocess.sh car yeongnam
./scripts/osrm-preprocess.sh foot yeongnam

docker compose up -d osrm
docker compose --profile walking up -d osrm-foot
```

전처리 순서는 `extract → partition → customize`다. 기존 결과가 있으면 스크립트는 덮어쓰지 않고 종료한다. 갱신할 때는 새 디렉터리에서 검증한 뒤 Compose가 참조하는 경로를 교체한다.

## 메모리 기준

- 영남권 도보 `extract` 피크: 약 1.75GB (현재 개발 환경 측정값)
- 전국 도보 그래프는 Docker 메모리 부족으로 종료될 수 있으므로, 현재 서비스 범위에서는 사용하지 않는다.

## 확인

```bash
docker compose --profile walking ps osrm osrm-foot
curl 'http://localhost:8080/api/courses?purposes=&duration=1n2d'
```

응답은 `recommendation_car_1`과 `recommendation_walk_1` 두 개이며, 각 항목의 `routePaths`는 실제 도로/보행 경로 좌표다. OSRM 좌표 요청 형식은 항상 `경도,위도` 순서다.

## 대중교통 확장 계획

OSRM은 자동차와 도보의 도로 그래프 전용으로 유지한다. 버스·도시철도 경로 탐색은 OSRM에 결합하지 않고, 시간표 기반의 별도 대중교통 엔진으로 구축한다. 이렇게 하면 외부 길찾기 API의 일일 쿼터 및 종량 과금에 추천 핵심 로직이 종속되지 않는다.

### 단계별 범위

| 단계 | 범위 | 경로 탐색 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | 부산 도시철도 정적 네트워크 | 역·노선·환승 그래프의 최단 시간 탐색 | 역-역 환승 경로와 총 소요시간 반환 |
| 2 | 부산 도시철도 시간표 | 출발 시각 기반 earliest-arrival 탐색 | 대기시간·막차를 포함한 경로 반환 |
| 3 | 부산 시내버스 정적 데이터 | 정류장·운행 패턴·환승을 같은 그래프에 적재 | 버스/도시철도 복합 경로 반환 |
| 4 | 부산 BIMS 실시간 정보 | 정적 시간표 결과의 도착 시각 보정 | 운행 지연을 반영한 ETA 표시 |
| 5 | 울산·경남 | 지역별 수집 어댑터 추가 | 부울경 통합 경로 반환 |

### 책임 분리

```text
출발지 좌표 ── 도보 OSRM ── 가까운 정류장 후보
                                  │
목적지 좌표 ── 도보 OSRM ── 가까운 정류장 후보
                                  │
                         대중교통 시간표 엔진
                                  │
             도보 / 도시철도 / 버스 / 환승 구간을 조합한 일정
```

- OSRM: 출발지·목적지와 정류장 사이의 도보 접근 경로, 자동차·도보 코스의 실제 도로 geometry.
- 대중교통 엔진: 정류장·노선·운행·환승 데이터에서 가장 이른 도착 경로를 계산.
- 실시간 데이터: 경로를 새로 계산하는 원천이 아니라 정적 결과의 도착예정시간 보정에 우선 사용.
- 외부 길찾기 API: 개발 검증 또는 장애 시 폴백 용도만 고려하고, 후보 탐색·이동시간 행렬에는 사용하지 않는다.

### 부산 도시철도 1차 설계

초기 데이터 모델은 향후 버스까지 수용할 수 있도록 `정류장(stop)` 중심으로 둔다. 도시철도에서는 역이 stop이고, 버스 단계에서 버스 정류장을 같은 모델에 추가한다.

| 데이터 | 1차 필드 | 버스 확장 시 추가 필드 |
| --- | --- | --- |
| stop | ID, 이름, 위도·경도, 유형, 운영기관 | 정류장 코드, 정류장 그룹 |
| line | ID, 이름, 색상, 교통수단 | 노선 방향·운영사 |
| line_stop | 노선별 정류장 순서, 다음 정류장 소요시간 | 운행 패턴(pattern) ID |
| transfer | 출발 stop, 도착 stop, 도보 환승시간 | 환승 제약·최소 환승시간 |
| trip / stop_time | - | 시간표 기반 출발·도착 시각 |

1차는 고정된 역간 소요시간과 기본 환승시간으로 다익스트라 탐색을 수행한다. 2차부터 실제 운행 시각을 읽어 출발시각 의존 earliest-arrival 탐색으로 교체한다. 이때 API 계약은 유지하고, 계산기 구현만 바꾼다.

### 운영 원칙

- 부산 도시철도 공식 데이터의 필드·라이선스·갱신 주기를 확인한 뒤 원본을 적재한다.
- 원본 응답은 수집 시점과 함께 보관하고, 서비스 API는 자체 DB만 조회한다.
- 데이터 수집 실패 시 마지막으로 성공한 데이터셋을 계속 제공한다.
- 버스 시간표가 완전하지 않은 지역은 배차간격 기반 추정치로 시작하되, 이를 실제 시간표 경로처럼 표시하지 않는다.
- 대중교통 경로 API는 코스 후보 생성용 행렬에 바로 투입하지 않는다. 정확한 시간표 엔진과 성능 검증 후에만 추천 점수에 반영한다.
