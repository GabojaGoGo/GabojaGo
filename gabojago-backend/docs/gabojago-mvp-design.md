# 가보자GO MVP 설계 공유 프롬프트

우리는 “가보자GO”라는 서비스를 기획하고 있다.

처음에는 국내여행 루트 추천 MVP로 시작하지만, 단순한 여행 앱으로 닫힌 구조를 만들면 안 된다.  
핵심은 나중에 카페 추천, 현재 위치 기반 장소 추천, 회식 장소 추천, 해장 루트, 데이트 코스, 문화 루트 등으로 확장 가능한 **상황 기반 장소·루트 추천 엔진**을 설계하는 것이다.

즉, 겉으로는 국내여행 추천 서비스지만 내부 구조는 다음 방향으로 잡아야 한다.

> 사용자 상황 + 목적 + 장소 카테고리·속성·적합도 + 현실 조건 + 추천 이유를 기반으로
> 실패 확률이 낮은 장소 또는 루트를 추천하는 서비스

---

## 1. 서비스의 핵심 문제 정의

기존 네이버지도, 카카오맵, 여행 앱들은 장소 정보는 많지만 다음 문제가 있다.

1. 추천 루트가 실제로 따라가기 어렵다.
   - 이동 동선이 비효율적이다.
   - 대중교통 이용자와 자차 이용자의 차이를 충분히 고려하지 않는다.
   - 주차 가능 여부, 도보 거리, 환승, 시간대, 이동 피로도 같은 현실 조건이 부족하다.

2. 장소 추천이 너무 표면적이다.
   - “카페”라고 해서 다 같은 카페가 아니다.
   - 여행지에서 가고 싶은 카페는 컴포즈커피 같은 일반 프랜차이즈가 아니라, 사진 찍기 좋은 카페, 데이트하기 좋은 카페, 조용히 쉬기 좋은 카페, 공부하기 좋은 일반 카페일 수 있다.
   - 기존 카테고리는 업종 중심이라 사용자의 목적을 잘 반영하지 못한다.

3. 사용자는 장소 정보를 찾고 싶은 게 아니라, 지금 상황에서 실패 확률이 낮은 선택지를 원한다.
   - 어디를 가야 할지
   - 어떤 순서로 움직여야 할지
   - 왜 이 루트가 나에게 맞는지
   - 이동이 힘들지는 않은지
   - 같이 가는 사람에게 적합한지
   - 주차나 대중교통은 괜찮은지

이런 부분을 세심하게 고려해주는 앱이 되어야 한다.

## 2. 가보자GO의 핵심 방향

가보자GO는 단순히 “국내여행 개인화 코스 추천 앱”이 아니다.

더 정확한 정의는 다음과 같다.

> 사용자의 상황, 목적, 이동수단, 시간대, 동행 유형을 고려해  
> 실패 확률이 낮은 장소와 루트를 추천하는 서비스

초기 MVP는 여행 루트 추천으로 시작한다.

하지만 내부 설계는 여행 전용으로 닫으면 안 된다.  
나중에 아래 기능으로 확장 가능해야 한다.

- 현재 위치 주변 추천
- 사진 찍기 좋은 카페 추천
- 공부하기 좋은 일반 카페 추천
- 데이트하기 좋은 카페 추천
- 회식 장소 추천
- 해장 루트 추천
- 문화생활 루트 추천
- 비 오는 날 대체 코스 추천
- 여행 중 대체 장소 추천

공통 구조는 다음과 같다.

```text
사용자 상황 파악
→ 목적 해석
→ 장소 후보 필터링
→ 현실 조건 검증
→ 점수 계산
→ 추천 이유 생성
→ 결과 카드 제공
```

## 3. MVP 단계 구분

### MVP 0단계: 추천 기준 설계

개발 전에 반드시 정해야 하는 단계다.

목표는 다음이다.

> 우리는 어떤 기준으로 좋은 장소와 좋은 루트를 판단할 것인가?

정해야 할 것:

- 좋은 루트의 기준
- 좋은 장소의 기준
- 사용자 상황 분류
- 장소 카테고리·속성·목적 적합도 분류 체계
- 이동 피로도 기준
- 추천 이유 문장 구조
- 루트 카드 구조

이 단계에서 가장 중요한 원칙은 다음이다.

> 장소의 업종 카테고리는 유지하고, 목적 적합도와 상황·시설 속성을 별도 축으로 관리해야 한다.

예를 들어 카페를 단순히 “카페” 하나로만 저장하면 안 된다.

기본 카테고리는 “카페”로 유지하면서 다음 목적·상황 적합도를 함께 가질 수 있어야 한다.

- 사진형 카페
- 데이트형 카페
- 공부형 카페
- 작업형 카페
- 대화형 카페
- 로컬형 카페
- 여행 감성 카페
- 주차형 카페
- 뷰 좋은 카페
- 조용한 카페

음식점도 마찬가지다.

- 해장형 음식점
- 회식형 음식점
- 부모님 동반 식당
- 가성비 식당
- 지역 대표 음식점
- 혼밥 가능 식당
- 데이트 식당
- 주차 쉬운 식당

### MVP 1단계: 국내여행 루트 추천

초기 출시용 핵심 MVP다.

범위는 너무 넓히지 않는다.

우선 다음 정도로 시작한다.

- 서울 출발 기준
- 당일치기 / 1박 2일
- 자차 / 대중교통
- 혼자 / 커플 / 친구 / 가족 등의 동행 구성
- 힐링 / 미식 / 사진 / 문화 / 액티비티 등의 핵심 목적
- 가성비 / 균형형 / 프리미엄 등의 예산 성향
- 초기 지역은 5~6개 정도로 제한

초기 후보 지역 예시:

- 강릉
- 춘천
- 속초
- 전주
- 경주
- 여수

전국을 처음부터 다 하려고 하면 추천 품질이 떨어진다.  
이 서비스는 추천이 틀리면 신뢰가 바로 깨지므로, 좁은 범위에서 품질을 높이는 게 중요하다.

#### MVP 1 사용자 입력 및 추천 흐름

기존의 단순 6단계 선택 흐름은 아래처럼 보완한다.

```text
1. 동행 구성 선택
   ↓
2. 일정·시간 선택
   ↓
3. 목적·스타일 선택
   ↓
4. 이동 조건 선택
   ↓
5. 지역 직접 선택 또는 추천받기
   ↓
6. 현실 제약 확인
   ↓
7. 맞춤 추천 결과
```

##### 1. 동행 구성 선택

`인원수`만으로는 부족하다. 2명이어도 커플, 친구, 부모·자녀에 따라 적합한 장소와 이동 피로도가 다르다.

| 대분류 | 중분류 | 소분류 |
|---|---|---|
| 인원 | 1명, 2명, 3~4명, 5명 이상 | 정확한 인원수 |
| 동행 관계 | 혼자, 커플, 친구, 가족 | 부부, 부모·자녀, 부모님 동반, 단체 |
| 특별 조건 | 영유아 동반, 고령자, 반려동물 | 유모차 필요, 휠체어, 긴 도보 불가 |

##### 2. 일정·시간 선택

| 대분류 | 중분류 | 소분류 |
|---|---|---|
| 기간 | 당일치기, 1박 2일 | MVP에서는 우선 두 종류만 지원 |
| 날짜 | 날짜 확정, 날짜 미정 | 평일·주말·성수기 판단 |
| 시간 | 출발시간, 복귀시간 | 예: 08시 출발, 22시 복귀 |
| 일정 밀도 | 여유롭게, 균형 있게, 알차게 | 하루 추천 장소 수 결정 |

##### 3. 목적·스타일 선택

`힐링`, `커플`, `가성비`, `문화`처럼 성격이 다른 값을 하나의 컨셉 목록에 섞지 않는다. 핵심 목적과 보조 스타일을 별도로 선택한다.

| 대분류 | 중분류 | 소분류 |
|---|---|---|
| 핵심 목적 | 힐링, 미식, 사진, 문화, 액티비티 | 1개 선택 |
| 보조 목적 | 자연, 카페, 로컬, 야경, 쇼핑, 역사 | 최대 2개 선택 |
| 여행 스타일 | 조용함, 유명한 곳, 숨은 명소 | 관광지 후보 점수 조정 |
| 예산 성향 | 가성비, 균형형, 프리미엄 | 예산 범위와 함께 사용 |

##### 4. 이동 조건 선택

| 대분류 | 중분류 | 소분류 |
|---|---|---|
| 이동수단 | 자차, 대중교통, 혼합 | 대중교통+도보, 자차+도보 |
| 출발지 | 현재 위치, 직접 입력 | 기차역·터미널 출발 선택 |
| 자차 제약 | 총 운전시간, 구간별 최대시간 | 주차 필수, 유료주차 허용 |
| 대중교통 제약 | 최대 도보, 최대 환승 | 버스 배차 간격, 막차 시간 고려 |

##### 5. 지역 직접 선택 또는 추천받기

지역을 반드시 직접 고르게 하지 않고 추천받기 선택지도 제공한다.

- 직접 선택: 광역시·도 → 시·군·구 → 권역·동네
- 지역 추천받기: 앞에서 선택한 조건을 기반으로 적합한 지역 후보 3개 제공
- MVP 범위: 강릉, 춘천, 속초, 전주, 경주, 여수 중 5~6개 검증 지역

##### 6. 현실 제약 확인

선택 화면을 너무 길게 만들지 않되, 결과 품질에 큰 영향을 주는 제약은 마지막 확인 화면에서 받는다.

- 1인당 또는 전체 교통·식사·숙박 예산
- 알레르기, 채식, 종교, 유아식 등 음식 제약
- 숙소 필요 / 숙소 제외 / 이미 숙소 예약
- 반드시 포함 / 반드시 제외할 장소
- 실내 선호, 반려동물 동반, 접근성 필요

##### 7. 맞춤 추천 결과

`여행지 / 코스 / 숙소 / 맛집`을 모두 같은 레벨의 결과로 두지 않는다. 추천 결과는 다음 계층으로 분리한다.

| 대분류 결과 | 중분류 | 사용 시점 |
|---|---|---|
| 지역 추천 | 조건에 맞는 여행 지역 후보 | 지역 추천받기를 선택한 경우 |
| 루트 추천 | 여러 장소를 조합한 여행 코스 | MVP의 핵심 결과 |
| 장소 추천 | 단일 장소 추천 | 여행 중 즉시 추천이나 대체 장소 |
| 장소 유형 | 관광지, 식당, 카페, 숙소 | 루트 또는 장소 추천 안에서 사용 |

숙소와 맛집은 독립된 최상위 추천 대상이 아니라, 루트 안의 `숙박`과 `식사` 슬롯에 들어가는 장소 유형으로 취급한다. 이 구조여야 같은 맛집이 코스와 맛집 결과에 중복 노출되는 문제를 막을 수 있다.

MVP 1의 결과물은 단순 장소 목록이 아니라 **루트 카드 3개**여야 한다.

예시:

```text
A. 바다 보며 쉬는 강릉 힐링 루트
B. 맛집과 카페 중심 전주 미식 루트
C. 사람 많은 곳 피하는 춘천 여유 루트
```

각 루트 카드에는 반드시 다음 정보가 들어가야 한다.

- 루트 이름
- 추천 이유
- 이동 피로도
- 예상 비용
- 자차/대중교통 적합성
- 장소 순서
- 장소별 역할
- 대체 장소
- 주의점

MVP 1의 핵심 차별점은 다음이다.

- 장소 목록 추천이 아니라 루트 추천
- 인기순 추천이 아니라 상황 기반 추천
- 이동시간만 보는 것이 아니라 이동 피로도 반영
- 자차/대중교통/주차/도보/환승 고려
- 카페/맛집의 업종 카테고리와 목적 적합도를 별도로 관리
- 왜 이 루트를 추천했는지 명확히 설명

### MVP 1.5단계: 여행 중 현재 위치 기반 추천

MVP 1 이후에 붙일 기능이다.

사용자가 여행지에 도착한 뒤 갑자기 필요한 장소를 추천한다.

예시 상황:

- 지금 근처에서 쉴 카페가 필요함
- 비가 와서 실내 장소가 필요함
- 숙소 체크인 전 시간이 남음
- 갑자기 배고픔
- 사진 찍을 만한 곳이 필요함
- 사람이 너무 많아서 대체 장소가 필요함
- 기존 루트 중 한 장소를 빼고 대체지가 필요함

추천 예시:

```text
지금 근처에서 갈 만한 곳

1. 사진 찍기 좋은 카페
2. 조용히 쉬기 좋은 카페
3. 비 오는 날 갈 만한 실내 장소
4. 숙소 체크인 전 시간 때우기 좋은 장소
5. 저녁 먹기 전 가볍게 산책할 곳
```

이 단계는 루트 추천이 아니라 **상황별 즉시 장소 추천**에 가깝다.

여행 전에는 루트 추천, 여행 중에는 현재 위치 기반 추천으로 앱을 다시 열 이유를 만든다.

### MVP 2단계: 목적 기반 장소 추천

여행이 아니어도 사용할 수 있는 추천으로 확장하는 단계다.

핵심은 다음이다.

```text
현재 위치 + 시간대 + 목적
```

예시:

- 지금 근처에서 노트북 하기 좋은 카페
- 지금 근처에서 조용히 대화하기 좋은 카페
- 지금 근처에서 데이트하기 좋은 카페
- 지금 근처에서 해장하기 좋은 식당
- 지금 근처에서 부모님 모시고 가기 좋은 식당
- 지금 근처에서 비 오는 날 갈 만한 곳
- 지금 근처에서 주차 쉬운 카페

이 단계부터 가보자GO는 여행 앱에서 상황 기반 장소 추천 앱으로 확장될 수 있다.

---

### MVP 3단계: 일상 루트 추천

여행 밖의 일상 루트 추천으로 확장하는 단계다.

예시:

- 회식 장소 추천
- 회식 후 2차 추천
- 해장 루트 추천
- 주말 데이트 코스
- 비 오는 날 실내 문화 코스
- 퇴근 후 가벼운 문화 루트
- 친구랑 반나절 놀기 루트

이 단계는 지금 바로 개발하지 않는다.  
다만 처음부터 구조는 열어둬야 한다.

---

## 4. 처음부터 절대 잘못 설계하면 안 되는 부분

### 1. 장소를 단순 카테고리로만 저장하면 안 됨

나쁜 설계:

```text
장소 = 카페
장소 = 음식점
장소 = 관광지
```

좋은 설계:

```text
장소 = 카페
태그 = 사진좋음, 조용함, 콘센트, 대화적합, 주차가능, 데이트적합
목적 = 공부, 데이트, 여행감성, 휴식, 사진
상황 = 비오는날, 저녁, 주말, 자차, 대중교통
```

장소 하나가 여러 목적에 쓰일 수 있어야 한다.

예시:

어떤 카페는 다음 조건에 동시에 해당할 수 있다.

- 사진 찍기 좋은 카페
- 데이트하기 좋은 카페
- 여행 감성 카페

하지만 공부하기 좋은 카페는 아닐 수 있다.

이런 다중 분류 구조가 필요하다.

---

### 2. 추천 대상을 Place와 Route로 분리해야 함

처음부터 추천 대상을 두 개로 나눠야 한다.

```text
Place 추천 = 지금 근처에서 어디 갈까?
Route 추천 = 오늘/내일 어떤 순서로 움직일까?
```

이걸 분리하지 않으면 나중에 현재 위치 추천과 여행 루트 추천이 꼬인다.

---

### 3. 사용자 입력을 그대로 쓰면 안 됨

사용자 입력은 내부적으로 “상황”과 “의도”로 변환해야 한다.

예시:

사용자 입력:

```text
커플, 힐링, 자차, 1박 2일
```

내부 해석:

```text
사진 장소 가점
카페 가점
이동 피로도 낮은 루트 가점
주차 가능 장소 가점
빡빡한 일정 감점
야경/산책 장소 약간 가점
```

이런 변환 계층이 있어야 나중에 회식, 해장, 문화 추천도 같은 방식으로 붙일 수 있다.

---

### 4. 추천 이유를 반드시 생성해야 함

가보자GO의 핵심 차별점은 “왜 추천했는지”다.

추천 결과에는 반드시 이유가 붙어야 한다.

예시:

```text
이 루트는 사용자가 선택한 힐링/미식 조건에 맞춰
바다 산책, 감성 카페, 지역 대표 음식을 포함했습니다.
장소 간 이동이 짧고 주차 가능한 장소 위주로 구성해
자차 이동 시 피로도를 낮췄습니다.
```

추천 이유는 단순 설명이 아니라 신뢰를 만드는 핵심 기능이다.

---

## 5. 추천 엔진의 공통 구조

여행, 카페, 회식, 해장, 문화 루트 모두 내부 구조는 동일하게 가져가야 한다.

```text
UserContext
→ Intent
→ Candidate Places
→ Constraint Filter
→ Scoring
→ Explanation
→ Result Card
```

### UserContext

사용자의 현재 상황이다.

포함 가능 값:

- 현재 위치
- 출발 위치
- 시간대
- 요일
- 이동수단
- 동행 유형
- 예산
- 여행 기간
- 날씨
- 선호 스타일
- 싫어하는 조건

### Intent

사용자의 목적이다.

예시:

- 여행하고 싶다
- 사진 찍고 싶다
- 쉬고 싶다
- 공부하고 싶다
- 데이트하고 싶다
- 해장하고 싶다
- 회식 장소를 찾고 싶다
- 부모님 모시고 가고 싶다

### Candidate Places

후보 장소다.

예시:

- 카페
- 음식점
- 관광지
- 문화시설
- 숙소
- 시장
- 공원
- 실내 장소

### Constraint Filter

현실 조건 필터다.

예시:

- 영업 중인가
- 너무 멀지 않은가
- 주차 가능한가
- 대중교통 가능한가
- 예산에 맞는가
- 지금 시간대에 적합한가
- 동행 유형과 맞는가
- 너무 많이 걷지는 않는가
- 환승이 너무 많지는 않은가

### Scoring

점수화 기준이다.

예시:

- 목적 적합도
- 이동 편의성
- 이동 피로도
- 시간대 적합도
- 동행 적합도
- 예산 적합도
- 장소 매력도
- 혼잡도
- 추천 설명 가능성

### Explanation

추천 이유다.

예시:

- 왜 이 장소인가
- 왜 이 순서인가
- 왜 이 사용자에게 맞는가
- 왜 다른 선택보다 나은가
- 어떤 조건 때문에 제외했는가

### Result Card

사용자에게 보여주는 결과다.

예시:

- 루트 카드
- 장소 카드
- 상황별 추천 카드
- 대체 선택지 카드

---

## 6. 초기 데이터 설계에서 필요한 핵심 개념

정확한 DB 설계는 나중에 더 구체화하더라도, 최소한 다음 개념은 처음부터 분리해야 한다.

### 분류 축을 섞지 않는 원칙

대분류·중분류·소분류는 하나의 거대한 트리로 만들지 않는다. 다음 다섯 축을 독립적으로 관리해야 중복과 의미 충돌을 막을 수 있다.

| 분류 축 | 질문 | 예시 |
|---|---|---|
| `PlaceCategory` | 이 장소는 무엇인가? | 카페, 식당, 관광지, 숙소 |
| `PlaceAttribute` | 이 장소는 어떤 특성이 있는가? | 조용함, 오션뷰, 주차 가능, 실내 |
| `Intent` | 사용자는 무엇을 하고 싶은가? | 힐링, 미식, 사진, 문화 |
| `UserContext` | 현재 누구와 어떤 상황인가? | 커플, 비 오는 날, 저녁, 아이 동반 |
| `Constraint` | 반드시 지켜야 할 조건은 무엇인가? | 최대 도보 20분, 주차 필수, 예산 10만원 |

예를 들어 `카페`는 장소 카테고리, `힐링`은 목적, `조용함`은 속성, `비 오는 날`은 상황, `주차 필수`는 제약이다. 이를 모두 `PlaceTag` 하나로 넣으면 같은 의미의 태그가 중복되고 추천 점수의 근거가 불명확해진다.

### 장소 카테고리 대·중·소분류

장소 카테고리는 장소당 하나의 대표 소분류를 기본값으로 두고, 여러 목적 적합성은 별도 속성이나 점수로 관리한다.

| 대분류 | 중분류 | 소분류 예시 |
|---|---|---|
| 관광 | 자연 | 해변, 산·숲, 강·호수, 공원·정원 |
| 관광 | 문화·역사 | 박물관, 미술관, 유적지, 사찰·종교시설 |
| 관광 | 체험·오락 | 액티비티, 테마파크, 축제, 시장 |
| 식음 | 식당 | 한식, 일식, 중식, 양식, 해산물, 지역특화 |
| 식음 | 카페·디저트 | 일반카페, 베이커리, 디저트, 로스터리 |
| 숙박 | 호텔·리조트 | 호텔, 리조트 |
| 숙박 | 소규모 숙소 | 펜션, 게스트하우스, 호스텔, 한옥, 모텔 |
| 이동 지원 | 교통 거점 | 기차역, 버스터미널, 공항 |
| 이동 지원 | 편의시설 | 주차장, 휴게소, 관광안내소 |

`뷰 좋은 카페`, `데이트 카페`, `조용한 카페`를 각각 카테고리로 만들지 않는다. 대표 카테고리는 `카페`로 유지하고 `SCENIC_VIEW`, `DATE_FRIENDLY`, `QUIET` 같은 속성을 복수로 연결한다.

### 장소 속성 대·중·소분류

| 대분류 | 중분류 | 소분류 예시 |
|---|---|---|
| 환경 | 공간 특성 | 실내, 실외, 바다뷰, 산뷰, 야경, 조용함 |
| 편의 | 시설 | 주차, 화장실, 콘센트, 유아시설, 반려동물, 배리어프리 |
| 운영 | 이용 조건 | 예약 필요, 늦게까지 영업, 평균 체류시간, 가격대 |
| 분위기 | 경험 특성 | 로컬, 감성, 트렌디, 전통, 한적함 |
| 적합성 | 동행 적합 | 혼자, 커플, 친구, 가족, 부모님, 아이 동반 |
| 적합성 | 상황 적합 | 비 오는 날, 야간, 겨울, 더운 날, 짧은 대기시간 |

속성은 가능하면 단순 boolean보다 `score`, `confidence`, `source`, `verifiedAt`을 함께 관리한다. 예를 들어 `QUIET=true`보다 `QUIET score=0.82, source=CURATED`가 추천 근거와 갱신에 유리하다.

### 목적 대·중·소분류

| 대분류 | 중분류 | 소분류 예시 |
|---|---|---|
| 휴식 | 힐링 | 자연 감상, 산책, 카페 휴식, 숙소 휴식 |
| 음식 | 미식 | 지역 음식, 카페 투어, 시장, 디저트 |
| 기록 | 사진 | 자연 풍경, 건축, 야경, 인물 사진 |
| 탐방 | 문화 | 역사, 전시, 공연, 지역 문화 |
| 활동 | 액티비티 | 수상, 레저, 트레킹, 체험 |

사용자는 핵심 목적 하나와 보조 목적 최대 두 개를 선택한다. `커플`은 목적이 아니라 동행 맥락이고, `가성비`는 목적이 아니라 예산 성향이므로 목적 목록에 넣지 않는다.

### 중복 방지용 코드 사전

태그와 분류값은 화면 문구가 아니라 고정 코드로 관리한다.

```text
표시 문구: 사진 맛집, 사진 찍기 좋음, 포토 스팟
표준 코드: PHOTO_FRIENDLY

표시 문구: 주차 가능, 전용 주차장, 차 가져가기 편함
표준 코드: PARKING_AVAILABLE
```

- 표준 코드는 중복 생성하지 않는다.
- 유사 표현은 `alias`로만 추가한다.
- 삭제 대신 비활성화해 기존 추천 이력을 보존한다.
- 카테고리, 속성, 목적, 상황 코드는 서로 다른 namespace를 사용한다.

### Place

장소 자체.

예시 속성:

- 장소명
- 주소
- 좌표
- 기본 카테고리
- 영업시간
- 가격대
- 평균 체류시간
- 대표 이미지
- 내부 장소 ID
- 원본 데이터 출처와 원천별 ID
- 마지막 수집일과 검증일

### PlaceAttribute

장소가 실제로 가진 시설·환경·분위기 속성. 하나의 장소에 여러 속성을 연결할 수 있다.

예시:

- `QUIET`
- `OUTDOOR`
- `INDOOR`
- `PARKING_AVAILABLE`
- `POWER_OUTLET`
- `OCEAN_VIEW`
- `LOCAL_ATMOSPHERE`
- `BARRIER_FREE`

### PlaceSuitability

특정 목적·동행·상황에 대한 적합도. 고정 사실이 아니라 점수와 근거로 관리한다.

예시:

- `PHOTO_FRIENDLY: 0.9`
- `DATE_FRIENDLY: 0.8`
- `FAMILY_FRIENDLY: 0.7`
- `RAINY_DAY_FRIENDLY: 0.6`
- `STUDY_FRIENDLY: 0.5`

### IntentType

사용자 목적.

예시:

- HEALING
- FOOD
- PHOTO
- CULTURE
- ACTIVITY
- SHOPPING

`DATE`, `FAMILY`는 동행·상황이고 `STUDY`, `HANGOVER`, `COMPANY_DINNER`는 여행 외 확장 목적이다. 이 값들은 MVP 2 이후 별도 intent group으로 추가한다.

### UserContext

추천 요청 당시의 사용자 상황.

예시:

- 위치
- 시간대
- 이동수단
- 동행 관계와 인원
- 예산
- 기간
- 일정 밀도
- 선호/비선호 조건

### Route

여러 장소를 순서대로 묶은 결과.

예시:

- 루트명
- 루트 목적
- 장소 순서
- 예상 이동시간
- 이동 피로도
- 예상 비용
- 추천 이유
- 대체 장소

### RecommendationReason

추천 이유.

예시:

- 사용자 목적과 맞는 이유
- 이동 동선이 좋은 이유
- 시간대가 적절한 이유
- 동행 유형과 맞는 이유
- 자차/대중교통 조건과 맞는 이유
- 예산과 맞는 이유

### 데이터 출처별 역할과 대안

한 API에서 모든 필드를 가져오려고 하지 않는다. 원천별 강점이 다르므로 필드 단위로 역할을 나눈다.

| 데이터 영역 | 1차 데이터원 | 보완·대안 | 활용 필드 | 한계 |
|---|---|---|---|---|
| 관광지·축제·문화·숙박 | [한국관광공사 TourAPI](https://www.data.go.kr/data/15101578/openapi.do) | 지자체 관광 데이터, 수작업 검수 | `contentId`, 이름, 주소, 좌표, 소개, 이미지, 관광 분류 | 분위기·목적 적합성은 직접 제공하지 않음 |
| 식당·카페·숙박 후보 | [Kakao Local API](https://developers.kakao.com/docs/latest/ko/local/dev-guide) | 지역 관광 데이터, 제휴 데이터 | 이름, 카테고리, 주소, 좌표, 거리, 장소 URL | 영업시간·주차·가격·분위기 정보가 부족함 |
| 자동차 이동 | [Kakao Mobility 길찾기](https://developers.kakaomobility.com/guide/navi-api/directions) | TMAP 자동차 길찾기 | 이동시간, 거리, 경유지 경로 | 자동차 기준이며 대중교통을 제공하지 않음 |
| 대중교통 이동 | [ODsay 대중교통 API](https://lab.odsay.com/guide/guide?platform=web) | SK Open API TMAP 대중교통, 지역별 공공데이터 | 도보시간, 환승, 버스·지하철·기차 경로 | 도시간 경로는 터미널 전후 도시내 경로를 추가 조합해야 함 |
| 날씨 | [기상청 단기예보](https://www.data.go.kr/data/15084084/openapi.do) | 날씨 미확정 시 계절 평균값 | 강수, 기온, 풍속, 하늘상태 | 장기 일정은 정확도가 낮아 재추천 필요 |
| 방문량·혼잡 보조지표 | 한국관광 데이터랩 API | 앱 내부 클릭·저장·완주 데이터 | 지역·시군구 방문자 추세, 혼잡 보정 | 실시간 장소별 혼잡도로 단정하면 안 됨 |
| 실제 분위기·목적 태그 | 운영자 수작업 검수 | 사용자 피드백, 제휴처 정보, 모델 추론 | 조용함, 사진 적합, 데이트 적합, 실제 주차 편의 | 주관적이고 변경되므로 신뢰도와 검증일 관리 필요 |
| 실시간 숙박 가격·재고 | 향후 OTA·숙박 제휴 API | MVP에서는 가격대 수작업 표기 | 가격, 객실 재고, 예약 링크 | TourAPI만으로 실시간 예약 가능 여부를 보장할 수 없음 |

현재 백엔드의 기본 조합은 다음과 같다.

```text
TourAPI
  → 관광지·축제·숙박·공식 이미지 후보

Kakao Local
  → 식당·카페·숙박·문화시설 후보 보강

Kakao Mobility
  → 자동차 구간별 실제 이동시간

관광 데이터랩
  → 지역·시군구 방문량 기반 혼잡 보정

ODsay 또는 TMAP 대중교통
  → 도보·환승·대중교통 이동시간

기상청 단기예보
  → 비·기온에 따른 실내외 장소 필터링

수작업 검수·사용자 피드백
  → 목적 태그와 API가 제공하지 않는 현실 정보
```

### 데이터 수집·정규화 파이프라인

외부 API 응답을 바로 추천 엔진에 넣지 않는다. 원본 보관과 서비스용 표준 장소를 분리한다.

```text
외부 API 원본 수집
→ 공통 포맷 정규화
→ 동일 장소 중복 병합
→ 카테고리 매핑
→ 속성·목적 적합도 생성
→ 수작업 검수
→ 추천 인덱스 반영
```

#### 1. 원본 수집

원천별 식별자를 보존한다.

```text
source = TOUR_API
sourcePlaceId = contentId
fetchedAt = 마지막 수집 시각
rawPayload = 필요한 원본 필드 또는 원본 저장 위치
```

같은 장소가 TourAPI와 Kakao Local에 모두 존재할 수 있으므로 `sourcePlaceId`를 서비스 내부 `placeId`로 직접 사용하지 않는다.

#### 2. 공통 포맷 정규화

API별 응답을 다음 공통 필드로 변환한다.

- 표준 장소명과 검색용 정규화 이름
- 도로명·지번 주소
- 위도·경도
- 대표 카테고리 코드
- 전화번호·공식 URL·제공처 장소 URL
- 이미지와 설명의 출처
- 마지막 수집일과 마지막 검증일

#### 3. 동일 장소 중복 병합

아래 순서로 동일 장소 여부를 판단한다.

1. 같은 데이터원에서 같은 `sourcePlaceId`면 동일 장소
2. 전화번호와 도로명주소가 같으면 동일 장소 후보
3. 정규화한 이름이 같고 좌표가 50m 이내면 동일 장소 후보
4. 이름이 같아도 주소가 다르면 체인점의 다른 지점일 수 있으므로 병합하지 않음
5. 자동 병합 확신이 낮으면 검수 대상으로 보냄

병합 시 필드별 우선 출처를 다르게 적용한다.

- 관광 설명·공식 이미지: TourAPI 우선
- 상업 장소 주소·좌표·카테고리: Kakao Local 최신값 우선
- 자동차 이동시간: Kakao Mobility
- 대중교통 경로: ODsay 또는 TMAP
- 수작업으로 검증한 값: 유효기간 동안 자동 수집값보다 우선

#### 4. 카테고리와 속성 생성

태그 생성 근거를 함께 저장한다.

| 생성 방식 | 의미 | 추천 신뢰도 원칙 |
|---|---|---|
| `SOURCE_RULE` | TourAPI·Kakao 카테고리를 규칙으로 변환 | 객관 카테고리에 사용 |
| `KEYWORD_RULE` | 설명·카테고리명 키워드로 추론 | 후보 태그로만 사용 |
| `MODEL_INFERRED` | 모델이 설명·이미지에서 추론 | 낮은 초기 신뢰도 부여 |
| `CURATED` | 운영자 또는 조사원이 검수 | 높은 신뢰도 부여 |
| `USER_FEEDBACK` | 방문자 피드백으로 보정 | 표본 수와 최신성을 함께 반영 |

모델이 `조용함`, `데이트 적합` 같은 주관적 태그를 생성할 수는 있지만, 이를 사실값처럼 확정하면 안 된다. `confidence`가 낮은 후보로 저장하고 수작업 또는 사용자 피드백으로 승격한다.

#### 5. 데이터 최신성

- 영업시간·휴무·가격: 짧은 유효기간
- 주소·좌표·카테고리: 중간 유효기간
- 자연·문화 장소 설명: 긴 유효기간
- 날씨·교통·혼잡: 요청 시점 또는 짧은 캐시
- 화면에는 필요한 경우 `마지막 확인일`을 표시

API 장애 시에는 마지막 정상 데이터를 사용하되, 실시간 정보라고 표시하지 않는다. 일정 생성 자체는 가능하게 유지하고 날씨·교통 정보만 확인 불가 상태로 내려주는 방식이 좋다.

### MVP 데이터 구축 순서

처음부터 전국 데이터를 완성하려 하지 않는다.

1. 검증 지역 5~6개를 확정한다.
2. TourAPI로 관광지·축제·숙박 후보를 수집한다.
3. 각 주요 거점 주변을 Kakao Local로 조회해 식당·카페 후보를 보강한다.
4. 지역별 상위 50~80개 장소만 수작업 검수한다.
5. 장소마다 대표 카테고리 1개와 핵심 속성 3~8개를 부여한다.
6. 자동차 루트부터 품질을 검증한다.
7. 대중교통 API를 붙여 도보·환승·도시간 이동을 별도 점수화한다.
8. 사용자 저장·제외·완주 피드백으로 태그와 점수를 갱신한다.

이 순서면 초기 250~480개의 검증 장소로 MVP를 운영할 수 있고, API에서 가져온 수만 개의 미검증 장소 때문에 추천 품질이 희석되는 것을 막을 수 있다.

## 7. 루트 추천에서 반드시 고려할 조건

루트 추천은 단순히 장소 점수 높은 순으로 뽑으면 안 된다.

중요한 것은 “장소들이 같이 묶였을 때 좋은 하루가 되는가”다.

루트 점수에는 최소한 다음 요소가 들어가야 한다.

```text
루트 점수 =
목적 적합도
+ 이동 효율
+ 이동 피로도
+ 일정 균형
+ 예산 적합도
+ 동행 적합도
+ 장소 매력도
+ 설명 가능성
```

### 이동시간과 이동 피로도는 다르게 봐야 한다

예를 들어 둘 다 30분 이동이어도 다르다.

```text
A: 자차 30분, 주차 쉬움
B: 버스 30분, 환승 2번, 도보 15분
```

둘 다 30분이지만 체감 피로도는 다르다.

따라서 이동 피로도에는 다음 요소가 들어가야 한다.

- 장소 간 이동시간
- 도보 거리
- 환승 횟수
- 대중교통 배차 문제
- 주차 가능 여부
- 주차장과 장소 간 거리
- 시간대 혼잡도
- 동행 유형에 따른 피로도

## 8. MVP 1에서 검증해야 할 것

MVP 1의 성공 기준은 기능 개수가 아니다.

사용자가 다음 반응을 보이는지가 중요하다.

- 이 루트 괜찮다.
- 내가 직접 짜는 것보다 편하다.
- 왜 추천했는지 이해된다.
- 카페/맛집 선택이 생각보다 세심하다.
- 네이버 검색보다 덜 피곤하다.
- 저장하거나 공유하고 싶다.
- 대중교통/자차 조건이 실제로 반영됐다고 느낀다.
- 루트가 현실적으로 따라갈 수 있다고 느낀다.

## 10. 최종 설계 원칙

가보자GO는 처음에는 국내여행 루트 추천 MVP로 시작한다.

하지만 내부 구조는 반드시 다음 방향이어야 한다.

```text
겉으로는:
국내여행 루트 추천 MVP

안쪽 구조는:
상황 기반 장소·루트 추천 엔진

초기 검증은:
서울 출발 당일/1박 2일 여행 루트 추천

확장 방향은:
여행 중 주변 추천
→ 목적 기반 장소 추천
→ 일상 상황 루트 추천
```

가장 중요한 설계 원칙은 다음이다.

> 여행 전용으로 닫힌 구조를 만들지 말고,  
> 사용자 상황 + 목적 + 장소 카테고리·속성·적합도 + 현실 조건 + 추천 이유 구조로 만들어야 한다.

이 구조로 설계해야 나중에 아이디어가 추가되어도 전체를 갈아엎지 않고 확장할 수 있다.
