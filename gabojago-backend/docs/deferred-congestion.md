# 보류 결정: 혼잡도 기능

## 결정

혼잡도는 필요 없는 기능이 아니라 **우선순위가 가장 나중인 기능**이다.
현재 데이터 구조로는 장소 단위 혼잡도를 만들 수 없으므로 기존 구현을 제거한다.
핵심 Attribute/Purpose 엔진을 완성한 뒤, 장소 단위·시간대 기반으로 다시 구현한다.

- 결정일: 2026-08-08
- 삭제 직전 코드 위치: 커밋 `74aaea8`

## 제거한 것

| 묶음 | 내용 |
| --- | --- |
| `tourism/data` | 혼잡도 수집·저장·조회, 관리자 API, 스케줄러, 엔티티 4개 (20개 파일) |
| `tourism/travel/spot` | 주변 관광지 조회, 혼잡도 예측·판정, 로그 (7개 파일) |
| `infrastructure/tourapi/TourApiClient` | DataLab 방문자수 조회 + areaBasedList2 페이징 |
| `infrastructure/region/RegionCodeMapper` | TourAPI 지역코드 ↔ DataLab 지역코드 매핑 (+ JSON 리소스) |

축제 조회(`/api/festivals`)는 제거 대상이 아니다. 개최 기간이 계속 바뀌어
사전 적재가 맞지 않으므로 `TourApiFestivalClient` 로 런타임 호출을 유지한다.

## 왜 지금 구조로는 안 되는가

기존 구현이 목적과 어긋난 지점은 세 가지다.

| 기존 구현 | 문제 |
| --- | --- |
| 시군구·광역 단위 방문자 수 | 장소 단위가 아니다. "이 카페가 조용한가"에 답할 수 없다 |
| `LocalDate.now().minusYears(1)` 기준 조회 | 오늘이 아니라 작년 같은 날짜 값이다 |
| 조회된 지역들 안에서의 상위 33% / 66% 백분위 | 절대 기준이 없어 조회 반경이 바뀌면 같은 장소의 라벨이 바뀐다 |

판정 로직(`buildThreshold`, `toCongestionLabel`)은 별도 클래스가 아니라
`SpotService` 내부 private 메서드로 묻혀 있어 재사용도 불가능한 상태였다.

`gabojago-mvp-design.md` 의 데이터 출처 표에도 데이터랩 방문자 추세를
"실시간 장소별 혼잡도로 단정하면 안 됨"으로 이미 명시해 두었다.

## 남겨 둔 자리

재구현 시 쓸 지점만 남긴다. 지금은 읽는 쪽도 쓰는 쪽도 없다.

- `AttributeKey.CROWD_LEVEL` — 장소 단위 혼잡도가 들어갈 자리.
  허용값 `RELAXED / NORMAL / CROWDED / VERY_CROWDED`
- `Region.datalabCode` — 삭제한 `RegionCodeMapper` 의 코드 매핑을
  테이블로 흡수할 자리. Python 적재는 현재 `NULL` 을 넣는다

## 다시 볼 조건

아래가 끝난 뒤에 착수한다. 그 전에는 붙일 대상(장소)과 붙일 자리가 없다.

```text
1. AttributeKey 커버리지 감사 (원천 / 변환 규칙 / 채움률)
2. 특성값 수집·매핑
3. Purpose 판정 규칙 설계·검수
   ─────── 여기까지가 목적 기반 탐색 엔진 ───────
4. 혼잡·웨이팅 등 현장 변수  ← 혼잡도 재구현
```

재구현 시 필요한 것은 삭제한 코드가 아니라 아래 두 가지다.

- 장소 단위 혼잡 신호의 원천 확보 (지역 단위 방문자 수로는 대체 불가)
- 요일·시간대 축. 하루 한 값이 아니라 "평일 오후 2시"를 구분할 수 있어야 한다

지역 단위 방문자 추세 자체는 장소 카드의 혼잡도가 아니라
여행 시기·지역 추천 쪽에서 별도로 검토한다.
